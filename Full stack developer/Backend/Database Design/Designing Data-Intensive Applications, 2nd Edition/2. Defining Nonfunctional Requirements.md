When building an application, you define **functional requirements** (what the app does) and **nonfunctional requirements** (performance, reliability, security, etc.). While functional needs are obvious, nonfunctional ones—like speed and maintainability—are equally crucial.

This chapter focuses on key nonfunctional requirements:

- **Performance** – Defining and measuring system speed.
- **Reliability** – Ensuring the system works despite failures.
- **Scalability** – Efficiently handling growth.
- **Maintainability** – Simplifying long-term system upkeep.

These concepts will be explored further, with a case study of a social networking service to illustrate performance and scalability in action.

# Case Study: Social Network Home Timelines

Imagine building a simplified social network like X (formerly Twitter), where users post messages and follow others.

Assuming **500 million posts per day** (5,700 per second on average, spiking to 150,000/second), and users having **an average of 200 followers**, the system must handle massive data flow efficiently—though some users have only a few followers, while celebrities have over 100 million.

## Representing Users, Post and Follows

![[Pasted image 20250322105133.png]]

```sql
SELECT posts.*, users.* FROM posts 
JOIN follows ON posts.sender_id=follows.followee_id 
JOIN users ON posts.sender_id=users.id 
WHERE follows.follower_id=current_user 
ORDER BY posts.timestamp DESC 
LIMIT 1000
```

Suppose we store all data in a relational database with tables for users, posts, and follow relationships.

The main read operation is the **home timeline**, displaying recent posts from followed users. A SQL query can fetch this data by joining the `posts`, `follows`, and `users` tables, sorting by timestamp, and limiting results to 1,000 posts.

To keep timelines updated, a client could **poll** every 5 seconds. With **10 million active users**, this results in **2 million queries per second**—a massive load. Since users follow an average of 200 people, this requires **400 million post lookups per second**, making the query extremely expensive, especially for users following thousands of accounts.

## Materializing and Updating Timelines

Instead of polling, the server should push new posts to online followers and precompute home timelines for fast access.

Each user has a **home timeline** storing recent posts from followed accounts. When a user posts, their post is **fanned out** to followers’ timelines. This reduces query load, as timelines can be served from a cache.

At 5,700 posts/sec with an average **fan-out** of 200, this results in 1M timeline writes/sec—far fewer than the 400M lookups needed otherwise. Spikes can be handled by **enqueueing** updates.

Celebrity posts pose a challenge; instead of inserting them into millions of timelines, they can be stored separately and merged at read time.

### How it works:

1. **For regular users** → Their posts are **pushed** to their followers’ timelines immediately (precomputed).
2. **For celebrities** → Their posts are stored in a **separate location**, and when a follower requests their timeline, the system **fetches and merges** the celebrity posts dynamically.

# Describing Performance

Software performance typically involves two key metrics:

- **Response Time**: The time from when a user makes a request to when they receive a response, measured in seconds, milliseconds, or microseconds.
- **Throughput**: The number of requests or amount of data the system can process per second, measured in "somethings per second."

In the social network case study, "posts per second" and "timeline writes per second" are throughput metrics, while "time to load the home timeline" or "time until a post is delivered" are response time metrics.

There’s often a trade-off between throughput and response time. As load increases, response time worsens due to queueing, as requests wait for processing. As throughput nears hardware limits, queueing delays increase sharply.

When a system is overloaded, it can enter a **vicious cycle** where response times grow, causing retries and further overload. This can lead to **metastable failure**—a state that might require rebooting or resetting the system.

To prevent overload, techniques like **exponential backoff**, **circuit breakers**, **load shedding**, and **backpressure** can be used. The focus of this section is on response time, while throughput and scalability will be discussed later.

# Latency and Response Time

In this book, we distinguish between **response time**, **service time**, and **latency**:

- **Response time**: What the client experiences, including all delays in the system.
- **Service time**: The active processing time of the request.
- **Latency**: Time during which a request is not actively processed, such as network delays.

Queueing delays happen when requests wait for resources, like CPU availability or network buffering. Latency refers to the time spent waiting for network transmission.

Response time can vary due to random factors like context switches or network issues. **Queueing delays** are a major contributor to this variability, especially when slow requests block faster ones, leading to **head-of-line blocking**. This delay is not part of service time and highlights the importance of measuring response times from the client side.

# Average, Median, and Percentiles

Response time should be viewed as a distribution, not a single value, because it varies with each request. Most requests are fast, but some are much slower (jitter).

The **mean** response time gives an average but doesn't reflect the typical user experience, so it's better to use **percentiles**. The **median** (50th percentile, p50) shows the typical response time, with half of the requests faster and half slower. Higher percentiles like **p95, p99, and p999** indicate how many requests are slower than a given threshold, highlighting outliers or tail latencies.

High percentiles matter because they affect user experience, especially for important customers. For example, Amazon uses the **99.9th percentile** for internal services, but optimizing the **99.99th percentile** may be too costly.

Studies show latency impacts user behavior, but data is inconsistent. For instance, a 400 ms delay in search results reduced traffic by 20% in one Google study, but a 400 ms increase only reduced searches by 0.6% in another. Other studies suggest that faster page load times may correlate with lower conversion rates, often due to irrelevant content loading quickly.

![[Pasted image 20250322105442.png]]

# Use of Response Time Metrics

High percentiles are crucial for backend services that require multiple calls to serve a single user request. A slow backend call can delay the entire request, even if other calls are fast, leading to **tail latency amplification**. This effect increases the chance of slow requests when multiple backend calls are needed.

Percentiles are used in **SLOs** and **SLAs** to define performance targets, such as setting a median response time or ensuring 99.9% of requests are error-free. SLAs specify consequences if targets aren't met.

To monitor percentiles, you can calculate them efficiently using algorithms like **HdrHistogram** or **t-digest**. Avoid averaging percentiles, as it is mathematically incorrect. Instead, aggregate histograms properly.

# Reliability and Fault Tolerance

Reliability in software means it performs as expected, tolerates user mistakes, handles the expected load and data volume, and prevents unauthorized access. It can be defined as "continuing to work correctly, even when things go wrong."

A **fault** occurs when a system part stops working (e.g., a malfunctioning hard drive), while a **failure** is when the entire system stops providing the required service, failing to meet its service level objective (SLO). A fault might not lead to failure if the system can tolerate it (e.g., a backup hard drive).

## Fault Tolerance

A fault-tolerant system continues to provide services despite certain faults. A **single point of failure (SPOF)** is a part of the system where a fault can cause the entire system to fail.

For instance, in the social network case, if a machine fails during the fan-out process, we ensure another machine can take over without losing or duplicating posts (known as exactly-once semantics).

Fault tolerance has limits, such as tolerating a few hard drive or node failures, but not an unlimited number. While some faults can't be prevented (e.g., security breaches), fault tolerance is crucial for handling recoverable faults. **Chaos engineering** tests fault tolerance by deliberately introducing faults to ensure the system can handle them.

## Hardware and Software Faults

Hardware failures are a common cause of system issues:

- **Hard drives** fail at a rate of 2-5% per year, meaning a large storage cluster can experience one failure per day.
- **SSDs** fail at a rate of 0.5-1% annually, with uncorrectable errors occurring about once per year.
- Other components like **power supplies, RAID controllers**, and **memory modules** also fail, though less often.
- Approximately **1 in 1,000 machines** has a CPU core that occasionally computes incorrectly, often due to defects.
- **RAM corruption** can occur from events like cosmic rays or defects, with more than 1% of machines encountering uncorrectable errors annually.

In large-scale systems, these hardware faults become common enough that they must be addressed as part of normal operations.

### Tolerating hardware faults through redundancy

To improve hardware reliability, redundancy is often added—e.g., RAID configurations for disks, dual power supplies for servers, and backup power for datacenters. While redundancy can reduce failures, component failures can still be correlated, making total server or datacenter outages more likely than expected.

Redundancy increases machine uptime, but distributed systems offer additional benefits by tolerating full datacenter outages. Cloud services focus on service availability by handling failures at the software level rather than individual hardware reliability. Fault tolerance techniques discussed in this book allow machines in different datacenters to take over during failures.

Multi-node systems also provide operational advantages, like performing rolling upgrades where one node is rebooted at a time without affecting service.

### Software faults

While hardware failures are often independent, software faults tend to be highly correlated, as many nodes run the same software and share similar bugs. These faults are harder to predict and can lead to widespread failures. Examples include:

- A bug causing simultaneous failure across nodes, such as the leap second bug in Java applications in 2012.
- A runaway process consuming too many resources, like memory.
- A dependent service becoming slow or unresponsive.
- Emergent behavior from interactions between systems.
- Cascading failures where one component's issue triggers failures in others.

Software bugs often remain dormant until an unusual set of conditions exposes an incorrect assumption. While there's no quick fix, solutions include better system design, thorough testing, process isolation, and monitoring in production.

## Humans and Reliability

Humans design, build, and operate software systems, bringing creativity but also unpredictability. Mistakes happen despite best intentions. Studies show that operator configuration changes are a leading cause of outages, more so than hardware failures.

Blaming human error is counterproductive—it’s often a symptom of systemic issues. Complex systems can exhibit unexpected interactions, leading to failures. Technical measures like thorough testing, rollback mechanisms, gradual deployments, and observability tools help mitigate mistakes, but many organizations prioritize features over resilience.

Blameless postmortems encourage learning from incidents without fear of punishment, leading to systemic improvements. Instead of simplistic answers like “Bob should have been more careful,” organizations should analyze how their sociotechnical system operates and improve it accordingly.

### How Important Is Reliability?

Reliability matters beyond critical systems—business applications, e-commerce, and personal data storage all depend on it. While brief outages may be tolerable, permanent data loss or corruption can be devastating.

For example, the Post Office Horizon scandal (1999–2019) saw hundreds wrongly convicted due to accounting software errors, leading to bankruptcies, wrongful imprisonments, and suicides. The assumption that computers always operate correctly had catastrophic consequences.

While there are cases where reducing reliability to cut costs is justifiable (e.g., prototyping), it’s crucial to be aware of the risks and potential impact.

# Scalability

A system working reliably today may not do so in the future, often due to increased load—more users, higher data volumes, or greater processing demands.

Scalability refers to a system’s ability to handle such growth. Some argue, “You’re not Google—just use a relational database.” Whether this applies depends on your application.

For early-stage products, simplicity and flexibility matter more than premature scaling efforts, which can waste resources or create rigid designs. Instead of asking if something "scales," consider:

- How can we handle future growth?
- What resources can we add to manage load?
- When will our current architecture reach its limits?

If your app gains traction, performance bottlenecks will reveal where scaling is needed—only then should scalability become a priority.

# Describing Load

To discuss scalability, we first need to define the system’s current load—typically measured by throughput (e.g., requests per second, data ingested per day, or checkouts per hour). Peak usage, read-to-write ratios, cache hit rates, or extreme cases may also influence scalability.

Once load is defined, we assess its impact:

1. How does performance change if load increases while resources remain fixed?
2. How much must resources increase to maintain performance?

The goal is to meet SLAs while minimizing costs. Ideally, doubling resources should handle twice the load (linear scalability), though real-world inefficiencies often cause costs to grow faster.

## Shared-Memory, Shared-Disk, and Shared-Nothing Architecture

The simplest way to scale a service is vertical scaling—moving to a more powerful machine with more CPU cores, RAM, and disk space. This shared-memory approach allows parallelism but becomes costly and inefficient at scale.

Another option is a shared-disk architecture, where multiple machines with independent CPUs and RAM access a shared storage array via NAS or SAN. However, contention and locking overhead limit scalability.

A more popular approach is shared-nothing (horizontal scaling), where each node has its own resources and coordination happens at the software level. This enables linear scalability, better price/performance, and fault tolerance but requires explicit sharding and adds distributed system complexity.

Some cloud-native databases separate storage and compute, resembling shared-disk but using a specialized API to avoid traditional scalability issues.

## Principles for Scalability

Large-scale system architectures are highly application-specific—there's no universal scalable design. A system handling 100,000 small requests per second differs greatly from one processing a few large ones, even with the same throughput.

As load grows, architectures must be re-evaluated at each order of magnitude. Planning beyond that is rarely useful.

A key principle is breaking systems into independent components, as seen in microservices, sharding, and shared-nothing architectures. However, knowing what to separate is crucial.

Simplicity matters—single-machine databases may be preferable to complex distributed setups, and predictable loads may not need auto-scaling. The best architectures balance pragmatism and complexity.

# Maintainability

Software does not wear out like mechanical objects, but it evolves due to changing requirements, environments, and the need for bug fixes. Most software costs come from maintenance—fixing bugs, ensuring reliability, adapting to new platforms, and managing technical debt.

Maintenance is challenging, especially for long-running systems using outdated technologies or lacking institutional knowledge. Additionally, software is deeply intertwined with the organizations it supports, making maintenance both a technical and human challenge.

All valuable systems eventually become legacy systems, so designing with maintenance in mind is crucial. Key principles include:

- **Operability**: Ensure smooth system operation.
- **Simplicity**: Use clear, consistent patterns to aid understanding.
- **Evolvability**: Enable future modifications and adaptations.

## Operability: Making Life Easy for Operations

Operations play a crucial role in reliability, often compensating for software limitations, while good software cannot function reliably with poor operations.

In large-scale systems, automation is essential but not a universal solution. While it reduces manual effort, edge cases still require skilled human intervention. More automation can make troubleshooting harder, so the right balance depends on the application and organization.

Good operability simplifies routine tasks, allowing teams to focus on high-value work. Key principles include:

- **Monitoring & Observability**: Tools to track key metrics and system behavior.
- **Redundancy**: No reliance on individual machines.
- **Clear Documentation**: Predictable and understandable operations.
- **Good Defaults & Overrides**: Sensible automation with manual control.
- **Self-Healing & Predictability**: Minimize surprises and enable smooth recovery.

## Simplicity Managing Complexity

As software projects grow, they often become complex and difficult to maintain, slowing development and increasing costs. High complexity raises the risk of bugs due to hidden assumptions and unintended interactions. Simplifying software improves maintainability and should be a key goal.

Defining simplicity is challenging, as it depends on perspective. Some complexity is inherent (essential), while some arises from tooling limitations (accidental), but this distinction shifts over time.

Abstraction is a powerful tool for managing complexity. Good abstractions hide intricate details behind clean interfaces, improving efficiency and software quality. Examples include high-level programming languages, SQL, and design methodologies like design patterns and domain-driven design (DDD). While this book focuses on general-purpose abstractions like database transactions, indexes, and event logs, these serve as a foundation for application-level abstractions.

## Evolvability: Making Change Easy

System requirements constantly change due to new insights, evolving use cases, shifting business priorities, and regulatory updates. Agile methodologies help adapt to change, supported by technical practices like test-driven development (TDD) and refactoring.

At the system level, **evolvability**—the ability to adapt easily—depends on simplicity and loose coupling. Complex, tightly integrated systems are harder to modify.

A key challenge in large systems is **irreversibility**—actions that cannot be undone increase risk. For example, a database migration is riskier if rollback isn’t possible. Minimizing irreversibility enhances flexibility.

# Summary

This chapter explored nonfunctional requirements—performance, reliability, scalability, and maintainability—introducing key principles and terminology.

We examined performance measurement (e.g., response time percentiles) and system load (e.g., throughput metrics) and their role in SLAs. Scalability ensures performance remains stable as load increases, often by breaking tasks into smaller, independent parts.

Reliability is achieved through fault tolerance, handling both hardware and software failures, and mitigating human errors with techniques like blameless postmortems.

Maintainability involves supporting operations, managing complexity, and enabling evolution. While there’s no single solution, using well-established abstractions helps. The rest of this book explores these foundational building blocks.
