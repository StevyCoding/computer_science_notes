A **Data-Intensive Application (DIA)** is software that primarily deals with large volumes of data, requiring efficient storage, processing, and retrieval mechanisms. These applications prioritize data management over computational complexity.

### Key Characteristics:

1. **High Data Volume** – Handles large datasets, often in terabytes or petabytes.
2. **Scalability** – Designed to scale horizontally (adding more machines) rather than just vertically (upgrading a single server).
3. **Distributed Systems** – Often rely on distributed databases, caching, and processing frameworks.
4. **High Throughput & Low Latency** – Optimized for fast data access and processing.
5. **Fault Tolerance** – Designed to handle hardware or software failures gracefully.

### Examples of Data-Intensive Applications:

- **Social Media Platforms** (Facebook, Twitter)
- **Streaming Services** (Netflix, YouTube)
- **E-commerce Platforms** (Amazon)
- **Big Data Analytics** (Hadoop, Spark)
- **AI & Machine Learning Systems**

## Analytical versus Operational Systems

**_Operational systems_ consist of the backend services and data infrastructure where data is created, for example by serving external users. Here, the application code both reads and modifies the data in its databases, based on the actions performed by the users._Analytical systems_ serve the needs of business analysts and data scientists. They contain a read-only copy of the data from the operational systems, and they are optimized for the types of data processing that are needed for analytics.**

### Characterizing Transaction Processing and Analytics

Databases handle various data types but generally follow a transaction-based access pattern. Operational systems perform **point queries** to retrieve, insert, update, or delete records based on user input. This interactive process is known as **online transaction processing (OLTP).**

Databases are increasingly used for analytics, which differs from OLTP. Analytic queries scan large datasets to compute aggregates (e.g., total revenue, sales trends, or product correlations). These insights aid business intelligence and are known as **online analytic processing (OLAP).**

| **Property**            | **Operational systems (OLTP)**                      | **Analytical systems (OLAP)**                 |
| ----------------------- | --------------------------------------------------- | --------------------------------------------- |
| Main read pattern   | Point queries (fetch individual records by key) | Aggregate over large number of records    |
| Main write pattern  | Create, update, and delete individual records   | Bulk import (ETL) or event stream         |
| Human user example  | End user of web/mobile application              | Internal analyst, for decision support    |
| Machine use example | Checking if an action is authorized             | Detecting fraud/abuse patterns            |
| Type of queries     | Fixed set of queries, predefined by application | Analyst can make arbitrary queries        |
| Data represents     | Latest state of data (current point in time)    | History of events that happened over time |
| Dataset size        | Gigabytes to terabytes                          | Terabytes to petabytes                    |

OLTP systems restrict custom SQL queries to protect data and maintain performance, relying on predefined queries in application code. In contrast, analytic databases allow users to write or generate queries using tools like Tableau or Power BI. Some systems, like Pinot, Druid, and ClickHouse, support real-time analytics for user-facing products.

# Data WareHousing

Initially, the same databases handled both OLTP and analytics, but by the 1990s, companies adopted **data warehouses** for analytics. Large enterprises run many independent OLTP systems (e.g., sales, inventory, HR), making direct querying inefficient due to **data silos**, unsuitable schemas, performance impact, and security concerns.

A **data warehouse** stores a read-only copy of OLTP data, optimized for analytics. Data is extracted, transformed, and loaded (**ETL**) or sometimes loaded first and transformed later (**ELT**), enabling efficient business analysis.

ETL processes often pull data from external SaaS APIs (e.g., CRM, email marketing) using tools like Fivetran or AirByte, enabling deeper analysis. **Hybrid Transactional/Analytic Processing (HTAP)** combines OLTP and analytics, but often consists of separate systems behind a unified interface. Despite HTAP, enterprises typically separate operational databases and a **single data warehouse** for cross-system analysis. Specialization increases with scale, as general-purpose systems struggle with demanding workloads.

## From Data warehouse to data lake

A **data warehouse** uses SQL-based relational models for business analytics but is less suited for data science tasks like **feature engineering** or **natural language processing**. Data scientists often prefer tools like Python (pandas, scikit-learn) or Spark.

To address this, organizations use **data lakes**, which store raw data from operational systems in various formats (Avro, Parquet, text, images, etc.), offering flexibility and cost efficiency. Data lakes can serve as a staging area for **data pipelines**, allowing users to transform raw data as needed (**"sushi principle"**: raw data is better).

A **data lakehouse** merges data lakes and warehouses, enabling SQL queries and machine learning on raw files using tools like **Apache Hive, Spark SQL, Presto, and Trino**.

## Beyond the data lake

As analytics mature, organizations focus on **DataOps**, governance, and compliance (e.g., GDPR, CCPA). Analytical data is now available as **event streams**, enabling real-time processing for faster responses (e.g., fraud detection).

**Reverse ETL** feeds analytics outputs into operational systems, creating **data products** like recommendation engines. Machine learning models trained on analytics data can be deployed using tools like **TFX, Kubeflow, or MLflow**.

## Systems of Record and Derived Data

This book distinguishes between **systems of record** and **derived data systems** to clarify data flow:

- **Systems of Record**: The authoritative source where data is first written (e.g., user input). It contains the correct, normalized version of data. Any discrepancies with other systems are resolved by the system of record.
- **Derived Data Systems**: These systems process or transform data from a system of record. They include caches, indexes, and models, and can be recreated from the original data. While redundant, they are essential for improving read query performance.

**Analytical systems** are typically derived data systems, while operational systems combine both system of record and derived data systems. The distinction depends on how data is used, not the database tool itself.

When derived data is updated, it must reflect changes in the original system of record, which often requires integration across multiple systems for consistency.

## Cloud versus Self-Hosting

The question of whether to **build in-house** or **outsource** depends on business priorities. Core competencies and competitive advantages should be handled internally, while routine tasks are better outsourced. For example, most companies don't generate their own electricity, as it's cheaper to buy it.

In software, decisions include **who builds** and **who deploys** the software. At one end of the spectrum is bespoke software, built and run in-house. On the other end are cloud services or SaaS products run by external vendors. The middle ground includes off-the-shelf software that you self-host, either on-premises or in the cloud (IaaS).

The choice of **deployment method** (cloud vs. on-premises) or **tools** like Kubernetes is less important for data system architecture and is beyond the scope of this book.

# Pro cons of cloud services

Using cloud services outsources software operation to the provider, offering benefits like time and cost savings. However, whether it's cheaper or easier than self-hosting depends on your skills and system workload. If you have the expertise and predictable load, self-hosting may be more cost-effective. If you're unfamiliar with the system, cloud services can be quicker and reduce staffing costs.

Cloud services can improve performance by leveraging operational expertise, but self-hosting allows for customizations. They are especially useful for workloads with fluctuating demands, like analytics, where resources can be scaled up or down easily.

However, with cloud services, you lose control. You can’t implement needed features, diagnose issues, or customize the service. If the service goes down, you must wait for recovery, and vendor lock-in can be a concern if the service becomes too expensive or changes in ways you don't like.

Despite these drawbacks, many organizations prefer cloud services for new applications, but in-house systems remain necessary for legacy systems or specialized requirements like high-frequency trading.

# Cloud-Native System Architecture

The rise of the cloud has changed data system implementation, shifting from buying hardware and software licenses to subscribing to a service. Cloud-native architecture is designed to take full advantage of cloud services.

While many self-hosted systems are now available as cloud services, cloud-native systems offer advantages, including better performance, faster recovery, easier scaling, and support for larger datasets.

## Layering of cloud services

Self-hosted data systems typically run on standard OSes like Linux or Windows, using CPUs, RAM, filesystems, and IP networks. Some require specialized hardware like GPUs or RDMA, but most rely on generic computing resources. In the cloud, such software runs on virtual machines with configurable CPU, memory, disk, and bandwidth, but requires self-administration.

Cloud-native services, in contrast, leverage managed cloud components. For example, object storage services (S3, Azure Blob, Cloudflare R2) abstract disk management by distributing data across multiple machines. Higher-level services, like Snowflake, build on these. Choosing between abstractions depends on whether existing solutions meet your needs or if a custom-built system is necessary.

**Separation of storage and compute**

Traditional computing treats disk storage as durable, using RAID for fault tolerance. In the cloud, local disks are often ephemeral, as they become inaccessible if an instance fails or is resized. Cloud services offer virtual disks (e.g., Amazon EBS, Azure managed disks), but these introduce network latency and overhead.

Cloud-native systems avoid virtual disks, relying on specialized storage services. Object storage (e.g., S3) handles large files, while databases manage smaller values separately. Unlike traditional systems where storage and computation are coupled, cloud-native architectures separate them, requiring data transfer over networks.

Cloud-native systems are often multitenant, sharing hardware across customers for efficiency, but requiring careful isolation for performance and security.

## Operations in the Cloud Era

Traditionally, database administrators (DBAs) and sysadmins managed server-side infrastructure. With DevOps, development and operations merged, and Google’s Site Reliability Engineers (SREs) embody this approach. Operations ensure service reliability, from configuring infrastructure to diagnosing issues.

Cloud services abstract individual machines, shifting focus from hardware management to service integration. Instead of capacity planning, operations now involve financial planning and cost optimization. Automation, ephemeral resources, and frequent updates are emphasized.

While cloud services reduce infrastructure management, challenges remain, including integration, security, performance monitoring, and troubleshooting. The cloud changes operations but does not eliminate its necessity.

# Distributed versus Single-Node Systems

A **distributed system** consists of multiple machines communicating over a network, each running a **node**. Reasons for using a distributed system include:

- **Inherent distribution**: Multi-user applications require network communication.
- **Cloud service interactions**: Data stored in one service must be transferred for processing in another.
- **Fault tolerance**: Redundant machines ensure availability if one fails.
- **Scalability**: Distributing load across machines handles growing data and compute needs.
- **Latency reduction**: Servers in different regions serve users faster.
- **Elasticity**: Cloud resources scale with demand, avoiding over-provisioning.
- **Specialized hardware**: Different tasks use optimized hardware (e.g., GPUs for ML, disk-heavy machines for storage).
- **Legal compliance**: Some laws require data to be stored within specific countries.

These factors apply to both custom applications and off-the-shelf software.

## Problems with Distributed Systems

**Downsides of Distributed Systems**

- **Network failures**: Requests can fail due to network issues, overload, or crashes, making retries tricky.
- **Latency**: Even in fast datacenters, network calls are much slower than in-process function calls.
- **Efficiency trade-offs**: Moving computation to where data resides is often faster than transferring large datasets. More nodes don’t always mean better performance.
- **Troubleshooting challenges**: Observability tools (e.g., OpenTelemetry, Zipkin, Jaeger) help diagnose performance issues but add complexity.
- **Data consistency issues**: Maintaining consistency across multiple databases is difficult; distributed transactions are rarely used in microservices due to independence concerns.

Given these challenges, single-machine solutions (e.g., DuckDB, SQLite, KùzuDB) can be simpler, cheaper, and sufficient for many workloads.

## Microservices and Serverless

**Client-Server and Microservices Architecture**

Most distributed systems use a **client-server model**, where clients send requests to servers, often via HTTP. A process can act as both a server (handling requests) and a client (making requests).

This model evolved into **service-oriented architecture (SOA)** and later **microservices**, where each service has a single responsibility, its own API, and a dedicated team. This allows independent updates and resource allocation while hiding implementation details behind an API. Services typically use separate databases to avoid coupling via shared storage.

However, microservices introduce complexity: deployment, monitoring, scaling, and testing require orchestration tools like Kubernetes. API evolution is also tricky, as changes can break clients. OpenAPI and gRPC help manage client-server interactions.

Microservices solve a **team coordination problem**—ideal for large organizations but often unnecessary for small teams. Simpler architectures are preferable when possible.

**Serverless (Function-as-a-Service, FaaS)** outsources infrastructure management to cloud providers, who allocate resources dynamically based on demand. This model **bills by usage** rather than machine instances, reducing operational overhead but introducing execution time limits, runtime restrictions, and cold start delays. Despite the name, serverless still runs on servers, just with automatic scaling and resource management.

# Cloud Computing versus Supercomputing

Cloud computing and high-performance computing (HPC) serve different purposes. **HPC (supercomputing)** is used for computationally intensive scientific tasks like weather forecasting and molecular dynamics, while **cloud computing** supports online services and business systems requiring high availability.

### Key Differences:

- **Workload Type**: Supercomputers run large batch jobs with periodic checkpoints, while cloud services must stay online continuously.
- **Communication**: HPC uses **shared memory and RDMA** for high-speed, trusted interactions; cloud computing relies on **IP/Ethernet** with stronger security measures.
- **Network Topology**: Cloud networks use **Clos topologies** for high bandwidth, while HPC employs **multi-dimensional meshes/toruses** for optimized workloads.
- **Geography**: Cloud nodes are **geographically distributed**, whereas supercomputers have **closely located nodes**.

Some analytics systems share HPC traits, but this book focuses on **high-availability services** (see “Reliability and Fault Tolerance”).

# Data Systems, Law, and Society

Data system architecture is shaped by technical goals, organizational needs, and societal responsibilities. Systems storing personal data face increasing scrutiny due to regulations like GDPR and CCPA, which grant individuals control over their data. Ethical considerations, such as the societal impact of automated decision-making (e.g., loans, job interviews, or criminal suspicion), are also critical. Engineers must balance legal compliance, ethical principles, and technical challenges, such as data deletion in immutable systems or derived datasets.

Data minimization, counter to "big data" practices, aligns with GDPR principles, emphasizing collecting only necessary data for specific purposes. Risks like liability, reputational damage, and legal fines must be weighed against storage benefits. Businesses, including payment processors and software vendors, face stricter compliance standards (e.g., PCI, SOC Type 2). Balancing business needs with user privacy and safety remains a key challenge, with deeper discussions on ethics, bias, and discrimination to follow.
