Data models are crucial in software development, shaping both how software is written and how problems are conceptualized.

Applications layer data models on top of one another:

- Developers model real-world entities (e.g., people, transactions) as objects or data structures.
- These structures are stored using general-purpose models like JSON, XML, relational tables, or graphs.
- Databases then represent this data as bytes in memory, disk, or networks.
- Hardware ultimately encodes bytes as electrical signals or magnetic fields.

Each layer abstracts complexity, enabling different teams to collaborate effectively. Different data models suit different use cases, and this chapter compares relational, document, graph, event sourcing, and dataframe models, along with query languages.

### Declarative Query Languages

Languages like SQL, Cypher, and SPARQL let users specify _what_ data they need rather than _how_ to retrieve it. This allows query optimizers to improve performance transparently. Unlike hand-coded algorithms, declarative queries can leverage parallel execution across CPUs or machines without extra effort.

# Relational Model versus Document Model

SQL, based on Edgar Codd’s 1970 relational model, organizes data into tables (relations) of rows (tuples). Initially theoretical, relational databases became dominant by the 1980s and remain widely used, especially in business analytics.

Over time, competing models like network, hierarchical, object, and XML databases emerged but never replaced SQL. Instead, SQL evolved, incorporating XML, JSON, and graph support.

The 2010s saw the rise of NoSQL, promoting schema flexibility, scalability, and open-source models. NewSQL aimed to combine NoSQL scalability with traditional relational guarantees. While NoSQL ideas influenced database design, the term has faded.

One major impact was the rise of the document model (e.g., JSON in MongoDB, Couchbase), which offers flexibility over relational tables. Next, we’ll explore the key trade-offs between document and relational databases.

## The Object-Relational Mismatch

Object-oriented programming languages often clash with SQL's relational model, creating an "impedance mismatch." This term, borrowed from electronics, refers to the inefficiency when connecting circuits with mismatched impedances, similar to the awkward translation needed between application objects and database tables.

### Object-relational mapping (ORM)

Object-relational mapping (ORM) frameworks aim to reduce the translation layer between application objects and database tables, but they are often criticized. Key issues include:

- ORMs can't fully hide the differences between the two models, so developers still need to think about both representations.
- ORMs are mainly used for OLTP apps, while data engineers working on analytics still need to deal with the underlying relational schema.
- ORMs often only support relational OLTP databases, lacking support for diverse data systems like search engines and NoSQL.
- Automatically generated schemas from ORMs may be awkward or inefficient for direct relational data access.
- ORMs can make it easy to write inefficient queries, like the N+1 problem.

However, ORMs also have advantages:

- They reduce boilerplate code for translating between objects and relations.
- Some ORMs provide caching to reduce database load.
- ORMs can help manage schema migrations and other administrative tasks.

### The document data model for one-to-many relationships

Not all data lends itself well to a relational representation. A LinkedIn profile can be expressed in a relational schema, with the profile identified by a unique user_id and fields like first_name and last_name as columns. However, one-to-many relationships like positions, education, and contact information are better represented in separate tables with foreign key references.

An alternative is to represent the profile as a JSON document, which may reduce the impedance mismatch between the application code and the storage layer. The JSON model has better locality, as all the relevant information is in one place. The one-to-many relationships form a tree structure, which is made explicit in the JSON representation.

The choice between the relational and document models depends on the specific use case. While the JSON representation works well for a typical user profile, for data with a genuinely large number of related items, the relational approach may be preferable to avoid an unwieldy embedded document.

## Normalization, Denormalization, and Joins

Why is region_id stored as an ID instead of a plain-text string in the LinkedIn profile example?

Storing an ID has several advantages over a plain-text string:

1. Consistent style and spelling across profiles
2. Avoiding ambiguity (e.g., distinguishing between "Washington" the state vs. the city)
3. Easier to update the region name in one place
4. Supports localization - the region name can be displayed in the viewer's language
5. Enables better search (e.g., finding people on the US East Coast)

Storing an ID is a more normalized representation, where the human-meaningful information (the region name) is stored in only one place. This avoids duplication and potential inconsistencies if the information needs to be updated.

The downside is that every time you want to display the region, you need to do an additional lookup to resolve the ID into the region name. In a relational database, this is done with a JOIN:

```sql
SELECT users.*, regions.region_name
FROM users
JOIN regions ON users.region_id = regions.id
WHERE users.id = 251;
```

In a document database like MongoDB, you can use the `$lookup` aggregation operator to perform the join:

```javascript
db.users.aggregate([
  { $match: { _id: 251 } },
  { $lookup: {
      from: "regions",
      localField: "region_id",
      foreignField: "_id",
      as: "region"
  } }
])
```

The trade-offs between normalization and denormalization apply here as well. Normalization reduces duplication and ensures consistency, but requires more joins. Denormalization improves read performance but complicates updates. The optimal choice depends on the specific use case and scale of the system.

### Denormalization in the social networking case study

In the "Case Study: Social Network Home Timelines", the materialized timeline is a cache of the result of the join between posts and follows, as the join was too expensive. The fan-out process that inserts a new post into followers' timelines was the way to keep the denormalized representation consistent.

However, the implementation of materialized timelines at X (formerly Twitter) does not store the actual post text. Instead, each entry only stores the post ID, the ID of the user who posted it, and some extra information. This is equivalent to the following query:

```sql
SELECT posts.id, posts.sender_id 
FROM posts
JOIN follows ON posts.sender_id = follows.followee_id
WHERE follows.follower_id = current_user
ORDER BY posts.timestamp DESC
LIMIT 1000
```

When the timeline is read, the service still needs to perform two joins: look up the post content and the sender's profile by ID. This process of looking up the human-readable information by ID is called "hydrating the IDs", and it is a join performed in application code.

The reason for storing only IDs is that the data they refer to, such as the number of likes and replies, is fast-changing. Denormalizing this information into the materialized timeline would significantly increase the storage cost, and the timeline should show the latest information when viewed.

This example shows that performing joins when reading data is not necessarily an impediment to creating high-performance, scalable services. Hydrating post ID and user ID is a scalable operation, as it parallelizes well and the cost doesn't depend on the number of accounts or followers.

The choice between normalization and denormalization is not straightforward. You need to consider how often the information changes and the cost of reads and writes. Normalization and denormalization are trade-offs in terms of performance and implementation effort.

## Stars and Snowflakes: Schemas for Analytics

Data warehouses are usually relational and have a few common table structures optimized for business analytics:

1. **Star schema**: The fact table at the center represents events (e.g., customer purchases), with foreign key references to dimension tables that provide context (e.g., product, store, date). This allows flexible analysis by joining the fact table with relevant dimensions.

2. **Snowflake schema**: A variation of the star schema where dimensions are further broken down into subdimensions, resulting in a more normalized structure.

Star schemas are often preferred over snowflake schemas as they are simpler for analysts to work with.

In a typical data warehouse:

- Fact tables can have hundreds of columns, capturing detailed information about each event.
- Dimension tables are also wide, storing all metadata that may be relevant for analysis.
- The schema consists mostly of many-to-one relationships, represented as foreign key references from the fact table to the dimension tables.
- Other relationship types may be denormalized to simplify queries, like folding multi-item transactions into separate rows in the fact table.

Some data warehouses take denormalization even further with the "one big table" (OBT) approach. This folds all dimension information directly into the fact table, trading off storage space for potentially faster queries. This is viable because data warehouses typically store historical data that is not frequently updated.

The star and snowflake schemas are optimized for the analytical needs of business users, in contrast to the operational needs of OLTP systems. The denormalization is less problematic in analytics, as consistency and write overhead are not as critical as in transactional systems.

## When to Use Which Model

The main arguments in favor of the document data model are schema flexibility, better performance due to locality, and closer alignment with the object model used by the application. The relational model counters by providing better support for joins and many-to-one/many-to-many relationships.

If the data has a document-like structure (a tree of one-to-many relationships), the document model is likely a good fit. Relational "shredding" (splitting the structure into multiple tables) can lead to cumbersome schemas and complicated application code.

However, the document model has limitations. You cannot directly reference nested items within a document - you can only access them by their position in the list. A relational approach works better for such direct references.

The document model also supports reorderable lists well, as items can be stored in a JSON array. Representing reorderable lists in a relational database requires tricks like sorting by an integer column or using a linked list of IDs.

Overall, the choice between the document and relational models depends on the structure of the data and the specific requirements of the application. The document model offers more flexibility, while the relational model provides better support for complex relationships and direct referencing of data.

### Schema flexibility in the document model

Most document databases and the JSON support in relational databases do not enforce any schema on the data in documents. This "schema-on-read" approach is in contrast with the "schema-on-write" approach of traditional relational databases, where the schema is explicit and enforced when data is written.

Schema-on-read is similar to dynamic (runtime) type checking in programming languages, while schema-on-write is like static (compile-time) type checking. Both approaches have their merits, and there's no universally right or wrong answer.

The difference is particularly noticeable when the application wants to change the data format. For example, say you want to store first and last name separately instead of a single full name field:

In a document database, you can just start writing new documents with the new fields, and handle the old format in the application:

```javascript
if (user && user.name && !user.first_name) {
    // Documents written before Dec 8, 2023 don't have first_name
    user.first_name = user.name.split(" ")[0];
}
```

The downside is that every part of the application needs to handle the old and new formats.

In a schema-on-write database, you would perform a migration:

```sql
ALTER TABLE users ADD COLUMN first_name text DEFAULT NULL;
UPDATE users SET first_name = split_part(name, ' ', 1);
```

This is fast for adding the column, but the UPDATE can be slow on large tables. Tools exist to perform such migrations without downtime, but they can still be operationally challenging.

The schema-on-read approach is advantageous if the data is heterogeneous - for example, if there are many different types of objects, or the structure is determined by external systems. In these cases, a schema may hurt more than it helps, and schemaless documents can be a more natural fit.

However, for data with a consistent structure, schemas are useful for documenting and enforcing that structure. We'll discuss schemas and schema evolution in more detail in Chapter 5.

### Data locality for reads and writes

Documents are stored as single continuous strings (JSON, XML, or binary format). This provides better performance when accessing entire documents, as it requires fewer disk seeks compared to retrieving data split across multiple tables.

However, this locality advantage only applies when accessing large portions of the document. Loading the entire document can be wasteful when only a small part is needed, and updates require rewriting the whole document. Best practice is to keep documents small and minimize frequent small updates.

The concept of data locality isn't exclusive to document databases. Relational databases (like Spanner and Oracle) and wide-column stores (like Bigtable) also provide ways to store related data together through nested tables and column families respectively.

The choice between these models should be based on your application's specific access patterns and requirements.

### Query languages for documents

Document and relational databases differ in their query languages. While relational databases use SQL, document databases vary in their query capabilities, from simple key-value lookups to rich query languages.

Here's an example comparing how to aggregate data (counting sharks sighted per month) in both types of databases:

PostgreSQL (SQL):

```sql
SELECT 
    date_trunc('month', observation_timestamp) AS observation_month,
    sum(num_animals) AS total_animals
FROM observations
WHERE family = 'Sharks'
GROUP BY observation_month;
```

MongoDB (Aggregation Pipeline):

```javascript
db.observations.aggregate([
    { $match: { family: "Sharks" } },
    { $group: {
        _id: {
            year:  { $year:  "$observationTimestamp" },
            month: { $month: "$observationTimestamp" }
        },
        totalAnimals: { $sum: "$numAnimals" }
    } }
]);
```

Both query languages are similarly expressive, with MongoDB using a JSON-based syntax instead of SQL's English-style syntax. The choice between them often comes down to personal preference and specific use case requirements.

### Convergence of document and relational databases

Document and relational databases have evolved to become more similar over time. Relational databases now support JSON types and document indexing, while document databases have added features like joins, secondary indexes, and declarative query languages.

This convergence benefits developers as both models have complementary strengths. Many applications need both the schema flexibility of document databases and the relational features like references and joins. Modern databases that combine both approaches (relational-document hybrids) offer a powerful solution.

Interestingly, Codd's original relational model included "nonsimple domains" - the ability to have nested relations (tables) as values, similar to today's JSON/XML support in SQL. This shows that the idea of combining structured and semi-structured data has been around since the beginning of relational databases.

# Graph-Like Data Models

Data models are distinguished by how they handle relationships. The document model works well for one-to-many relationships (tree-structured data), but when many-to-many relationships become common, a graph model might be more appropriate.

A graph consists of:
- Vertices (nodes/entities)
- Edges (relationships/arcs)

Common graph examples include:
1. Social networks (people and their connections)
2. Web pages (pages and their links)
3. Transportation networks (junctions and routes)

Graphs can be represented through:
- Adjacency lists (each vertex stores neighboring vertex IDs)
- Adjacency matrices (2D array showing connections)

Graphs are particularly powerful because they can store different types of objects in a single database. For example, Facebook's graph contains various vertex types (people, locations, events) and edge types (friendships, check-ins, comments).

Popular graph models include:
- Property graphs (Neo4j, Memgraph)
- Triple-stores (Datomic, AllegroGraph)
- Query languages: Cypher, SPARQL, Datalog, GraphQL

The choice between document, relational, or graph models depends on the complexity and type of relationships in your data.

## Property Graphs
Here's a shorter version:

A property graph model consists of:

Vertices (nodes) have:
- Unique ID
- Label (type of object)
- Outgoing/incoming edges
- Properties (key-value pairs)

Edges (relationships) have:
- Unique ID
- Start vertex (tail)
- End vertex (head)
- Label (type of relationship)
- Properties (key-value pairs)

A graph store can be represented as two relational tables:
1. Vertices table (storing node information)
2. Edges table (storing relationship information)

A property graph model consists of vertices and edges, both with properties. This can be represented using two relational tables:

```sql
CREATE TABLE vertices (
    vertex_id   integer PRIMARY KEY,
    label       text,
    properties  jsonb
);

CREATE TABLE edges (
    edge_id     integer PRIMARY KEY,
    tail_vertex integer REFERENCES vertices (vertex_id),
    head_vertex integer REFERENCES vertices (vertex_id),
    label       text,
    properties  jsonb
);

CREATE INDEX edges_tails ON edges (tail_vertex);
CREATE INDEX edges_heads ON edges (head_vertex);
```

Key features:
1. Any vertex can connect to any other vertex
2. Efficient traversal in both directions (via indexes)
3. Different types of relationships can coexist in the same graph
4. Flexible for modeling complex relationships

Limitations:
- Edges can only connect two vertices (for higher-degree relationships, additional vertices are needed)

The model is highly flexible and evolvable - new types of relationships can be added without changing the schema. For example, a social network could be extended to include food allergies by adding allergen vertices and connecting them to person vertices with "is_allergic_to" edges.

## The Cypher Query Language

Here’s a more concise version with the key details and the Cypher code included:

---

**Cypher** is a query language for property graphs, originally developed for Neo4j and later standardized as openCypher. It is supported by Neo4j, Memgraph, KùzuDB, Amazon Neptune, Apache AGE (PostgreSQL-based), and others. Named after a character in _The Matrix_, it is unrelated to cryptographic ciphers.

The following Cypher query inserts a subset of a location-person graph:

```sql
CREATE
  (namerica :Location {name:'North America',  type:'continent'}),
  (usa      :Location {name:'United States',  type:'country'}),
  (idaho    :Location {name:'Idaho',          type:'state'}),
  (lucy     :Person   {name:'Lucy'}),
  (idaho) -[:WITHIN ]-> (usa) -[:WITHIN]-> (namerica),
  (lucy)  -[:BORN_IN]-> (idaho);

```

To find people who emigrated from the US to Europe:

```
MATCH
  (person) -[:BORN_IN]->  () -[:WITHIN*0..]-> (:Location {name:'United States'}),
  (person) -[:LIVES_IN]-> () -[:WITHIN*0..]-> (:Location {name:'Europe'})
RETURN person.name;

```

This query finds people born in the US and now living in Europe by following `WITHIN` edges to determine locations. It can be executed by scanning all people or starting with indexed locations and working backward.

## Graph queries in SQL

Here’s a concise and clearer version of your text while keeping the key points and SQL code:

---

Graph data can be stored in a relational database, but querying it using SQL is cumbersome. Every edge traversal requires a join, and in graph queries, the number of traversals is often unknown in advance.

Cypher simplifies this with patterns like `(:Location {name:'United States'}) -[:WITHIN*0..]-> ()`, meaning "follow `WITHIN` edges zero or more times," similar to the `*` operator in regular expressions. In SQL, recursive common table expressions (`WITH RECURSIVE`) achieve the same result but are far more complex.

### SQL Equivalent of a Cypher Query

The following SQL query finds people born in the US who now live in Europe:

```sql
WITH RECURSIVE
  in_usa(vertex_id) AS (
      SELECT vertex_id FROM vertices
      WHERE label = 'Location' AND properties->>'name' = 'United States'
    UNION
      SELECT edges.tail_vertex FROM edges
      JOIN in_usa ON edges.head_vertex = in_usa.vertex_id
      WHERE edges.label = 'within'
  ),
  in_europe(vertex_id) AS (
      SELECT vertex_id FROM vertices
      WHERE label = 'Location' AND properties->>'name' = 'Europe'
    UNION
      SELECT edges.tail_vertex FROM edges
      JOIN in_europe ON edges.head_vertex = in_europe.vertex_id
      WHERE edges.label = 'within'
  ),
  born_in_usa(vertex_id) AS (
    SELECT edges.tail_vertex FROM edges
    JOIN in_usa ON edges.head_vertex = in_usa.vertex_id
    WHERE edges.label = 'born_in'
  ),
  lives_in_europe(vertex_id) AS (
    SELECT edges.tail_vertex FROM edges
    JOIN in_europe ON edges.head_vertex = in_europe.vertex_id
    WHERE edges.label = 'lives_in'
  )
SELECT vertices.properties->>'name'
FROM vertices
JOIN born_in_usa ON vertices.vertex_id = born_in_usa.vertex_id
JOIN lives_in_europe ON vertices.vertex_id = lives_in_europe.vertex_id;

```

### Comparison with Cypher

This SQL query, spanning **31 lines**, is equivalent to the **4-line** Cypher query:

```
MATCH
  (person)-[:BORN_IN]->() -[:WITHIN*0..]->(:Location {name:'United States'}),
  (person)-[:LIVES_IN]->() -[:WITHIN*0..]->(:Location {name:'Europe'})
RETURN person.name;

```

The right query language significantly simplifies graph operations. Future SQL standards may integrate a graph query language like GQL, inspired by Cypher, GSQL, and PGQL, to improve graph querying in relational databases.

## Triple-Stores and SPARQL

### **Summary of Triple-Stores and RDF with Code Examples**

Triple-stores are similar to property graphs but use a different structure: all data is stored as **triples**:

**(subject, predicate, object)**

- **Subject**: Like a vertex in a graph.
- **Predicate**: Like an edge label (relationship).
- **Object**: Either another vertex (edge) or a value (property).

For example:

- `(lucy, birthYear, 1989)` → Lucy has a property `birthYear = 1989`.
- `(lucy, marriedTo, alain)` → Lucy is connected to Alain via `marriedTo`.

### **Turtle Format (Triples in RDF)**

```
@prefix : <urn:example:>.
_:lucy     a :Person;   :name "Lucy";   :bornIn _:idaho.
_:idaho    a :Location; :name "Idaho";  :type "state";   :within _:usa.
_:usa      a :Location; :name "USA";    :type "country"; :within _:namerica.
_:namerica a :Location; :name "North America"; :type "continent".

```

- **`:bornIn` & `:within`** define relationships between entities.
- **Semicolons (`;`)** avoid repetition by grouping properties.

---

### **RDF/XML Representation**

More verbose, but structured:

```xml
<Person rdf:nodeID="lucy">
    <name>Lucy</name>
    <bornIn rdf:nodeID="idaho"/>
</Person>
<Location rdf:nodeID="idaho">
    <name>Idaho</name>
    <type>state</type>
    <within rdf:nodeID="usa"/>
</Location>

```

- **`rdf:nodeID`** ensures unique references.
- **`<within rdf:nodeID="usa"/>`** shows hierarchy.

---

### **SPARQL Query Language**

Similar to **Cypher** but for RDF databases.

### **Example: Find people born in the US & now living in Europe**

```
PREFIX : <urn:example:>

SELECT ?personName WHERE {
  ?person :name ?personName.
  ?person :bornIn / :within* / :name "United States".
  ?person :livesIn / :within* / :name "Europe".
}

```

- `?person :bornIn / :within* ?location.` → Matches **variable-length paths** like Cypher’s `WITHIN*0..`.
- `?usa :name "United States".` → Filters locations named "United States".

---

### **Key Takeaways**

- Triple-stores store **graph-like** data as **triples** (subject-predicate-object).
- RDF can be represented in **Turtle, XML, JSON-LD**, etc.
- **SPARQL** is an expressive query language for **RDF triple-stores** (like Cypher for property graphs).
- Supported by **Amazon Neptune, Blazegraph, Virtuoso, Apache Jena**, etc.

## **Datalog: Recursive Relational Queries**

Datalog is a declarative query language from the 1980s, mainly used in niche databases like Datomic, LogicBlox, CozoDB, and LinkedIn’s LIquid. Unlike SPARQL and Cypher, which are graph-based, Datalog is rooted in relational databases but excels in recursive queries, making it useful for graph traversal.

### **Key Concepts:**

- **Facts:** Represent data, similar to rows in relational tables. Example:
    
    ```prolog
    location(2, "United States", "country").
    born_in(100, 3).  /* Lucy was born in Idaho */
    
    ```
    
- **Rules:** Define how to derive new data, acting like virtual tables (similar to SQL views). Example:
    
    ```prolog
    within_recursive(LocID, PlaceName) :- location(LocID, PlaceName, _).
    migrated(PName, BornIn, LivingIn)  :- person(PersonID, PName),
                                          born_in(PersonID, BornID),
                                          within_recursive(BornID, BornIn),
                                          lives_in(PersonID, LivingID),
                                          within_recursive(LivingID, LivingIn).
    
    ```
    
- **Recursion:** Unlike SQL, Datalog naturally supports recursive rules, making it powerful for hierarchical and graph-based queries.
    

### **Comparison with Other Query Languages:**

- **Cypher & SPARQL** start with `SELECT`like queries.
- **Datalog** builds logic step-by-step using recursive rules, similar to Prolog.

Though not widely adopted in mainstream databases, Datalog’s expressiveness and recursion capabilities make it a strong choice for complex queries, especially in graph-based and logic-driven applications.

## GraphQL

GraphQL is a query language designed primarily for client applications (such as mobile or web apps) to request structured JSON data from servers. It provides flexibility for frontend developers by allowing them to specify exactly what data they need, reducing over-fetching and under-fetching.

### **Key Features:**

- **Client-Driven Queries:** Clients request only the data they need, making UI development more flexible.
- **JSON Responses:** The response mirrors the query structure, ensuring predictable results.
- **Limited Query Capabilities:**
    - No recursion support (unlike SQL, Cypher, SPARQL, or Datalog).
    - No arbitrary search conditions unless explicitly implemented in the schema.
    - Focuses on fetching structured data rather than complex analytical queries.
- **Common Use Cases:**
    - Fetching UI-related data, like chat messages with sender details.
    - Reducing API versioning issues by allowing frontend modifications without backend changes.

### **Trade-offs:**

- **Requires Additional Tooling:** Needs middleware to convert queries into backend service calls (e.g., REST, gRPC).
- **Potential Performance Concerns:** Authorization, rate limiting, and query complexity must be managed to prevent excessive server load.
- **Duplication in Responses:** Prefers simplicity for UI rendering over response size optimization.

GraphQL is database-agnostic—it can be implemented on top of relational, document, or graph databases. Its strength lies in efficiently fetching structured data for client applications rather than complex querying.

# Event Sourcing CQRS

In complex applications, a single data representation may not be sufficient for all queries. Instead, data can be **written in one form** and **derived into multiple read-optimized representations**.

### **Key Concepts:**

1. **Event Log as a Source of Truth**
    - Data is written as immutable events (e.g., JSON objects with timestamps).
    - Events are **appended** to a log rather than modified or deleted.
    - Example: A conference management system logs every change (e.g., seat bookings, cancellations).
2. **Materialized Views (Projections)**
    - Derived from the event log to optimize reads.
    - Different views can be maintained for different use cases (e.g., dashboard stats, attendee badge printing).
3. **Event Sourcing**
    - Expresses all state changes as **events** (e.g., “Seats were booked”).
    - Events are **replayable**—past events can be processed again to rebuild derived views.
4. **Command Query Responsibility Segregation (CQRS)**
    - **Commands** modify state (e.g., a booking request).
    - **Queries** read optimized data from materialized views.

### **Advantages:**

✅ **Clearer Intent:** Events explicitly describe what happened (e.g., “Booking was cancelled” is clearer than modifying multiple database rows).

✅ **Reproducibility:** If a bug occurs, materialized views can be deleted and rebuilt by replaying events.

✅ **Multiple Read Models:** Views can be structured for specific queries (e.g., fast lookups vs. analytics).

✅ **Evolvability:** New views and event types can be added without modifying existing data.

✅ **Auditability:** The event log maintains a complete history of system changes.

### **Challenges:**

⚠ **Handling External Data:** Events relying on external sources (e.g., currency exchange rates) need to store historical values to ensure consistency.

⚠ **Privacy Concerns:** Immutable logs may contain personal data that cannot be easily deleted (GDPR compliance challenge).

⚠ **Side-Effects on Reprocessing:** Care is needed to avoid unintended consequences (e.g., re-sending confirmation emails when rebuilding views).

### **Implementations:**

- **Databases**: PostgreSQL (MartenDB), EventStoreDB, Axon Framework.
- **Streaming Platforms**: Apache Kafka for event storage and real-time processing.

The main requirement is **ensuring all views process events in the exact order they appear in the log**, which can be difficult in distributed systems.

# **Dataframes, Matrices, and Arrays**

### **Dataframes and Multidimensional Arrays in Analytical Contexts**

While data models such as relational tables and graphs are commonly used in both transactional processing and analytics, **dataframes** and **multidimensional arrays** are specific models that excel in analytical and scientific contexts but are rare in OLTP systems.

### **Dataframes:**

- **What They Are**:
    - Dataframes are tabular data structures used widely in data science, particularly in tools like R, Python’s Pandas, Apache Spark, and others.
    - They are useful for data exploration, statistical analysis, data visualization, and preparing datasets for machine learning models.
- **Operations on Dataframes**:
    - Dataframes support operations like filtering, grouping, aggregating, and joining (often referred to as "merge").
    - They are manipulated through command-based operations, making them a natural fit for **data wrangling** by data scientists.
- **Advantages Over Relational Databases**:
    - Dataframes are more flexible than relational databases and can handle complex operations beyond SQL.
    - They can transform data from relational formats into other representations, such as matrices or multidimensional arrays, which are ideal for machine learning algorithms.

### **Transformation to Matrices**:

- **Example**:
    - A relational table with users and movie ratings can be transformed into a matrix, where rows represent users and columns represent movies.
    - This matrix might be sparse, meaning many user-movie combinations are missing. This sparse matrix representation works well with dataframes and libraries like NumPy.**Handling Non-Numerical Data**:
- **Dates**: Transformed into floating-point numbers within a specified range.
- **Categorical Data**: **One-hot encoding** is used for columns with a limited set of categories (e.g., movie genres). A separate column is created for each possible genre, and each movie has a `1` in the column corresponding to its genre and `0`s in others. This approach can easily handle movies that belong to multiple genres.
- **Matrix Representation**:
    - Once transformed into numerical matrices, the data becomes compatible with linear algebra operations, which are core to machine learning algorithms (e.g., recommendations based on user preferences).

### **Multidimensional Arrays (Matrices)**:

- **Scientific Use**:
    - Some databases, such as **TileDB**, specialize in storing large multidimensional arrays of numbers, known as **array databases**.
    - These are commonly used in fields like **geospatial analysis** (raster data), **medical imaging**, and **astronomy**.
- **Financial Use**:
    - Dataframes are also widely used in **finance** for time series data, such as **asset prices** and **trades** over time.

### **Key Points**:

1. **Dataframes** are highly flexible and allow data to be gradually transformed from a relational model into other forms, such as matrices or multidimensional arrays.
2. **Matrices** are used in machine learning and scientific fields because they are optimized for linear algebra operations.
3. **One-hot encoding** and transformations help convert categorical and non-numerical data into a form suitable for analysis or machine learning.
4. **Array databases** like TileDB are specialized for storing and working with large scientific datasets, such as geospatial and time-series data.

# Summary

### **Overview of Data Models**

In this chapter, we’ve explored a broad range of data models, each designed to address different requirements in various domains. While we didn't dive deeply into every model, this overview should provide a solid foundation for understanding which model best fits your application's needs.

### **Key Data Models Discussed:**

1. **Relational Model**:
    - Despite being over 50 years old, the relational model remains central to many applications, especially in **data warehousing** and **business analytics**.
    - **Relational star or snowflake schemas** and **SQL** are commonly used in these fields.
2. **Document Model**:
    - Designed for use cases where data is stored in self-contained JSON documents, and relationships between documents are rare.
3. **Graph Data Models**:
    - Targeted at use cases where everything is potentially related to everything else.
    - Ideal for situations requiring **recursive queries** to traverse relationships (e.g., **Cypher**, **SPARQL**, **Datalog**).
4. **Dataframes**:
    - Generalizes relational data by allowing for many columns, bridging the gap between relational databases and **multidimensional arrays** used in **machine learning**, **statistical data analysis**, and **scientific computing**.

### **Emulation of Data Models**:

- While it’s possible to emulate one model in terms of another (e.g., representing graph data in a relational database), it’s often inefficient or awkward. For instance, handling **recursive queries** in **SQL** can be cumbersome.

### **Specialized Databases**:

- Specialist databases have been created for each model, optimized for specific use cases. However, relational databases, document databases, and even some graph databases are increasingly adding support for **other models**. For example:
    - **Relational databases** now support JSON columns for document data.
    - **Document databases** offer relational-like joins.
    - **SQL databases** are enhancing support for graph data.

### **Event Sourcing**:

- Event sourcing uses an **append-only log of immutable events**, which is beneficial for modeling activities in complex business domains. This log is turned into **read-optimized materialized views** using **CQRS**.

### **Schema Flexibility**:

- Non-relational models usually don’t enforce a schema, making them adaptable to changing application requirements. Still, your application will likely assume a certain structure, whether the schema is **explicit** (enforced on write) or **implicit** (assumed on read).

### **Other Notable Data Models**:

While we have covered many data models, there are others not discussed in this chapter, including:

- **Genome Data**: Used for **sequence-similarity searches** in DNA analysis. Specialized software like **GenBank** is built for this purpose.
- **Ledger Models**: Common in **financial systems** and **cryptocurrency blockchains**, where **double-entry accounting** is used. Databases like **TigerBeetle** specialize in this type of data model.
- **Full-Text Search**: A key aspect of **information retrieval**, often used alongside databases. Topics like **search indexes** and **vector search** are worth exploring further, although we won't dive deep into them here.

### **Looking Ahead**:

- In the next chapter, we'll explore the **trade-offs** involved in implementing the data models described here, helping you understand the practical challenges and considerations when choosing the right model for your system.

### **Conclusion**:

The landscape of data models is vast and constantly evolving. Understanding these models and how they fit different use cases will allow you to choose the best one for your application, whether you are handling transactional data, scientific data, or complex event-driven architectures.
