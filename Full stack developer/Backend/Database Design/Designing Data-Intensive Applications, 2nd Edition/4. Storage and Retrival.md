At its core, a database has two main tasks: storing the data you give it and retrieving that data when you ask for it later.

In Chapter 3, we covered data models and query languages—how data is input and retrieved. This chapter shifts focus to how databases handle storage and retrieval internally. As an application developer, understanding how the database stores and finds data is essential for choosing the right storage engine for your needs. While you likely won’t build a storage engine yourself, knowing the basics helps you configure the engine for optimal performance based on your workload.

There’s a key difference between storage engines optimized for transactional workloads (OLTP) and those optimized for analytics. This chapter first explores two OLTP storage engine types: **log-structured storage engines**, which write immutable data files, and **B-tree engines**, which update data in-place. These engines are used for both key-value storage and secondary indexes.

Later, we’ll dive into **storage engines for analytics** and discuss **advanced indexes**, like those used for text search.

# Storage and indexing for OLTP

Here's a simplified database implemented in Bash with two functions: `db_set` to store data and `db_get` to retrieve it.

```bash
#!/bin/bash

# Store key-value pair in the database
db_set () {
    echo "$1,$2" >> database
}

# Retrieve value for a given key
db_get () {
    grep "^$1," database | sed -e "s/^$1,//" | tail -n 1
}

```

### How It Works:

- **`db_set key value`** appends a key-value pair (separated by a comma) to a text file (the database).
- **`db_get key`** looks up the most recent value associated with that key by scanning the file.

Example usage:

```bash
$ db_set 12 '{"name":"London","attractions":["Big Ben","London Eye"]}'
$ db_set 42 '{"name":"San Francisco","attractions":["Golden Gate Bridge"]}'
$ db_get 42
{"name":"San Francisco","attractions":["Golden Gate Bridge"]}

```

### Storage Format:

The database is a simple text file where each line is a key-value pair (like a CSV file). New entries are appended at the end, and previous values for the same key are not overwritten.

```bash
$ db_set 42 '{"name":"San Francisco","attractions":["Exploratorium"]}'
$ db_get 42
{"name":"San Francisco","attractions":["Exploratorium"]}

$ cat database
12,{"name":"London","attractions":["Big Ben","London Eye"]}
42,{"name":"San Francisco","attractions":["Golden Gate Bridge"]}
42,{"name":"San Francisco","attractions":["Exploratorium"]}

```

### Performance Consideration:

- The **`db_set`** function is efficient because appending to a file is fast.
- However, **`db_get`** has poor performance with large datasets. It scans the entire file to find the key, leading to an O(n) time complexity. As the database grows, the lookup time increases linearly.

### Indexing:

To speed up lookups, we need an **index**, which organizes data in a way that allows for faster searches. Indexing improves query performance but comes with trade-offs:

- **Read performance**: Indexes speed up data retrieval.
- **Write performance**: Indexes slow down write operations because they need to be updated each time data is added.

Databases require manual index configuration based on your query patterns. While indexes help with reading efficiency, they consume additional disk space and increase the cost of writes.

This is a key trade-off in database design: you balance the benefits of fast queries with the overhead introduced by maintaining indexes.

# Log-Structured Storage

To improve read performance in our simple database, we can store the most recent value's location in memory using a hash map. This hash map stores the **key** as the key, and the **byte offset** in the log file (where the value is stored) as the value. Here's the updated approach:

### Code:

```bash
#!/bin/bash

# In-memory hash map to store key-to-byte offset mapping
declare -A hash_map

# Store key-value pair in the database and update hash map
db_set () {
    echo "$1,$2" >> database
    hash_map[$1]=$(wc -c < database)  # Store the byte offset of the latest entry
}

# Retrieve value for a given key using the hash map
db_get () {
    local offset=${hash_map[$1]}
    if [ -z "$offset" ]; then
        echo "Key not found"
        return
    fi
    # Seek to the offset and read the value
    dd if=database bs=1 skip=$offset count=100 2>/dev/null | sed -e "s/^$1,//"
}

```

### How It Works:

1. **`db_set`**: Stores the key-value pair in a file and updates the hash map with the byte offset of the newly written key-value pair.
2. **`db_get`**: Uses the hash map to quickly find the byte offset and retrieves the value from the file, making the read much faster if the data is cached.

### Example Usage:

```bash
$ db_set 12 '{"name":"London","attractions":["Big Ben","London Eye"]}'
$ db_set 42 '{"name":"San Francisco","attractions":["Golden Gate Bridge"]}'
$ db_get 42
{"name":"San Francisco","attractions":["Golden Gate Bridge"]}

```

### Advantages:

- **Fast Reads**: The hash map allows for quick lookups by byte offset, reducing disk I/O if the data is cached.

### Problems:

1. **Disk Space**: Old log entries aren’t removed, so the file may grow indefinitely.
2. **Non-Persistent Hash Map**: The hash map doesn’t survive restarts, so rebuilding it by scanning the log file can be slow for large datasets.
3. **Memory Limit**: The hash map must fit in memory. Storing it on disk is difficult due to random access and resizing issues.
4. **Inefficient Range Queries**: For operations like scanning keys in a range, you'd need to manually look up each key, making such queries slow.

In summary, using a hash map for quick lookups boosts read performance but introduces challenges related to persistence, memory, and disk space management.

### The SSTable file format

In databases, hash tables are not typically used for indexing. Instead, data is often stored in sorted structures, one of the most common being the **Sorted String Table (SSTable)**. An SSTable stores key-value pairs sorted by key, ensuring that each key appears only once.

### Key Features of SSTable:

- **Sorted Data**: Keys are sorted, allowing efficient searches.
- **Sparse Index**: Instead of indexing every key, only the first key in each block of data is indexed, creating a sparse index.
- **Compression**: Each block of data can be compressed, reducing disk space and I/O bandwidth, though at the cost of more CPU time.

### Code Example:

```bash
#!/bin/bash

# Simulate SSTable with sorted key-value pairs
declare -A sstable
declare -A sparse_index

# Store key-value in sorted SSTable
db_set () {
    sstable[$1]=$2
    # Update the sparse index with the first key of each block (for simplicity, assuming 1 key per block here)
    sparse_index[$1]=$2
}

# Retrieve value by key from SSTable
db_get () {
    echo ${sstable[$1]}
}

# Retrieve block via sparse index
db_block_lookup () {
    first_key=$(echo ${sparse_index[$1]})
    echo "Scanning from block starting with key: $first_key"
    # Perform block scan (simulation)
}

```

How It Works:

1. **`db_set`**: Stores key-value pairs in the SSTable, maintaining a sparse index with only the first key of each block.
2. **`db_get`**: Retrieves a value by looking up the key in the SSTable.
3. **`db_block_lookup`**: Uses the sparse index to quickly find the starting point of the relevant block.

Advantages:

- **Efficient Range Queries**: Because the data is sorted, you can quickly identify the relevant block and scan it efficiently.
- **Lower Memory Use**: No need to store all keys in memory, reducing the memory footprint.
- **Compression**: Blocks are compressed, saving disk space and reducing I/O.

Drawbacks:

- **Compression Overhead**: While compression saves space, it increases CPU usage for data retrieval.
- **Write Complexity**: Adding new entries requires re-sorting or inserting into appropriate blocks, making writes slower compared to simple append-only systems.

In summary, using an SSTable with a sparse index allows for fast lookups and efficient range queries while keeping memory use low. However, it introduces complexity in managing writes and compression overhead.

### Constructing and merging SSTables

SSTables improve read efficiency but make writes harder since appending unsorted data breaks the order. LSM-Trees solve this by combining **in-memory structures** with **immutable sorted files**.

**How LSM-Trees Work**

1. **Writes**: New data is first stored in an **in-memory tree** (memtable) like a red-black tree or skip list.
2. **Flushing to Disk**: Once the memtable exceeds a threshold, it is **written to disk** as a new **sorted SSTable segment**, while a new memtable starts accepting writes.
3. **Reads**: First check the memtable, then search SSTable segments from newest to oldest.
4. **Compaction (Merging)**: Background process **merges** SSTables, keeping only the latest values and discarding deleted entries (**tombstones**).

---

**Code Example (Simplified LSM-Tree in Bash)**

```bash
#!/bin/bash

declare -A memtable  # In-memory store
log_file="db.log"    # Append-only log for durability
sst_dir="sstables"   # Directory for SSTable segments

mkdir -p "$sst_dir"

# Append to log and memtable
db_set () {
    echo "$1,$2" >> "$log_file"
    memtable[$1]=$2
}

# Search in memtable, then SSTables
db_get () {
    if [[ -n ${memtable[$1]} ]]; then
        echo ${memtable[$1]}
        return
    fi
    grep "^$1," "$sst_dir"/* | tail -n 1 | cut -d',' -f2-
}

# Flush memtable to SSTable
flush_memtable () {
    sst_file="$sst_dir/sst_$(date +%s).txt"
    for key in "${!memtable[@]}"; do
        echo "$key,${memtable[$key]}" >> "$sst_file"
    done
    rm "$log_file"  # Clear log after persisting
    memtable=()     # Reset memtable
}

```

---

**Key Benefits**

✅ **Efficient Writes**: Writes go to an in-memory structure, then flushed in bulk.

✅ **Fast Reads**: Sorted SSTables enable quick lookups.

✅ **Crash Recovery**: Logs allow restoring the latest state.

✅ **Compaction Keeps Size Manageable**: Merging removes old versions and deleted keys.

This approach is used in **RocksDB, Cassandra, Scylla, and HBase**, based on **Google’s Bigtable**. The idea originated as **LSM-Trees** (Log-Structured Merge-Trees) in 1996 and is now widely adopted in modern databases.

### Constructing and merging SSTables

SSTables make reading efficient but complicate writing since new data must be kept in order. Simply appending new entries would break the sorting, and rewriting the whole file each time would be too slow.

To solve this, we use a **log-structured approach**:

1. New writes go into an **in-memory ordered structure** (memtable).
2. When it fills up, it’s saved as a **sorted SSTable on disk**, leaving older SSTables intact.
3. Reads check the **memtable first**, then search SSTables from newest to oldest.
4. A background **compaction process** merges SSTables, removing duplicates and deletions (tombstones).

To prevent data loss, every write is also appended to a **separate log**, which helps restore the memtable after crashes.

This approach, called the **Log-Structured Merge-Tree (LSM-Tree)**, is used in databases like **RocksDB, Cassandra, and HBase**. It allows efficient writes while keeping reads fast through compaction and indexing.

### Bloom filters

Reading old or missing keys in LSM storage can be slow because the database must check multiple SSTable files. To speed this up, **Bloom filters** are used.

A **Bloom filter** is a compact data structure that quickly tells whether a key _might_ exist in an SSTable:

1. When a key is added, a **hash function** sets certain bits in a small **bitmap**.
2. To check if a key exists, the same hash is used.
    - If any required bits are **0**, the key **definitely** isn’t in the SSTable.
    - If all bits are **1**, the key _might_ be there, but false positives can occur.

This approach saves time by skipping unnecessary SSTable lookups while allowing occasional extra checks when false positives happen. In practice, allocating **10 bits per key** keeps false positives below **1%**, and adding **5 more bits** reduces errors **tenfold**.

## B-trees

B-trees are the most widely used data structure for key-value storage, especially in relational databases. Unlike log-structured indexes, which use immutable segments, B-trees organize data in fixed-size pages (e.g., 4–16 KiB) and allow in-place updates.

Each page has a unique **page number** and can reference other pages, forming a **tree structure**:

1. **Root page** → Points to child pages containing key ranges.
2. **Leaf pages** → Store actual key-value pairs or references to their locations.

To find a key, start at the root and follow references until reaching a leaf page. The **branching factor** (number of child references per page) is typically in the hundreds, keeping the tree **shallow** (3–4 levels deep) even for large databases.

When adding a key:

- If the target page is **full**, it **splits** into two, and the parent is updated.
- If the parent is full, **splitting** may continue up to the root.

This ensures the tree stays balanced, maintaining **O(log n) lookup time**. A 4-level B-tree with 4 KiB pages and a branching factor of 500 can store up to **250 TB** of data.

### B-tree variants

Over time, several B-tree variations have emerged:

- **Copy-on-Write (COW):** Instead of overwriting pages and using a WAL for crash recovery, databases like LMDB write modified pages to a new location and update parent pages accordingly. This also helps with concurrency.
- **Key Abbreviation:** To save space, interior nodes store only partial keys, increasing the branching factor and reducing tree depth.
- **Optimized Disk Layout:** Some implementations try to keep leaf pages sequential on disk for faster range scans, though maintaining this order as the tree grows is challenging.
- **Sibling Pointers:** Leaf pages may link to their left and right siblings, allowing efficient in-order scans without returning to parent pages.

## Comparing B-Trees and LSM-Trees

LSM-trees excel in write-heavy workloads, while B-trees offer faster reads. However, performance depends on the specific workload, so testing is essential. Some storage engines even combine both approaches, using multiple B-trees with LSM-style merging. Next, we’ll explore key factors in measuring storage engine performance.

### **Read performance**

B-trees provide fast and predictable reads by accessing a small number of pages. LSM-trees may require checking multiple SSTables, but Bloom filters reduce disk I/O. Range queries are efficient in B-trees but costlier in LSM-trees since Bloom filters don’t help. High write loads can cause latency spikes in LSM storage if compaction lags, leading to backpressure that temporarily halts reads and writes. Both approaches can achieve high read throughput on SSDs, but efficient parallelism handling is crucial.

### Sequential vs. random writes

B-trees scatter writes across disk pages, causing random writes, while LSM-trees write large sequential segments, improving write throughput. Sequential writes are much faster than random writes, especially on HDDs. SSDs reduce this gap but still perform better with sequential writes due to flash memory’s block erasure process. Random writes trigger more garbage collection, reducing available bandwidth and increasing wear on the drive.

### Write **amplification**

Every write request generates multiple I/O operations.

- **LSM-trees** write data to a log, then to the memtable, and again during compaction. If values are large, they can be stored separately to reduce overhead.
- **B-trees** write data at least twice: once to the write-ahead log and again to the tree page. Sometimes, an entire page is rewritten even for small changes to ensure crash recovery.

**Write amplification** measures how much extra data is written compared to a simple append-only log. Higher write amplification reduces throughput and accelerates SSD wear. LSM-trees usually have lower write amplification since they avoid full-page writes and can compress data.

When testing storage engines, it’s important to run experiments long enough to account for write amplification. Initially, LSM-trees may seem fast, but as the database grows, compaction starts consuming disk bandwidth, affecting performance.

### Disk space usage

- **B-trees** can become fragmented over time, with unused pages remaining in the database file. Free pages can be reused but not easily returned to the OS. To address this, databases like PostgreSQL use background processes (e.g., vacuum) to reorganize pages.
- **LSM-trees** handle fragmentation better since compaction rewrites data, eliminating unused space. SSTables allow better compression, often leading to smaller disk usage compared to B-trees. However, size-tiered compaction requires more temporary disk space.

Data Deletion Challenges:

- In LSM-trees, deleted records may persist in higher levels until compaction fully removes them, which can take time. Some storage engines optimize for faster deletion propagation.
- The immutable nature of SSTables simplifies database snapshots and backups since segment files can be referenced without copying. In contrast, B-trees overwrite pages, making efficient snapshots more difficult.

### Fragmentation and Data Retention

Primary vs. Secondary Indexes

- **Primary indexes** uniquely identify rows, documents, or vertices, allowing efficient lookups and reference resolution.
- **Secondary indexes** enable searches by non-primary columns. In relational databases, they are created using `CREATE INDEX`.

Implementing Secondary Indexes:

- Unlike primary indexes, values in secondary indexes may not be unique. This is handled by:
    - Storing a list of matching row IDs (similar to full-text index postings).
    - Appending row IDs to make entries unique.
- Both B-trees (in-place updates) and log-structured storage can implement secondary indexes.

### Storing values within the index

**Index Keys and Values**

- **Clustered Index:** Stores actual data within the index (e.g., MySQL InnoDB primary keys).
- **Heap File Approach:** Stores references to data, either by primary key (e.g., InnoDB secondary indexes) or direct disk location (e.g., PostgreSQL heap files).
- **Covering Index:** Stores selected columns in the index for faster lookups but increases disk usage.

Updating records can be simple if the new value fits in place but may require moving data and updating references if it exceeds available space.

### Keeping everything in memory

Disks are durable and cost-effective but require careful data layout for performance. As RAM becomes cheaper, in-memory databases have emerged, keeping all data in memory for speed.

Some, like Memcached, are used for caching and tolerate data loss. Others, like VoltDB and Redis, ensure durability via logging, snapshots, or replication. Despite writing to disk, these databases serve all reads from memory, avoiding disk-related overhead.

Their speed advantage comes from skipping on-disk data structure management, not just avoiding disk reads. They also enable complex data models, like Redis’s priority queues and sets, which are harder to implement on disk.

# Data Storage for Analytics

Data warehouse vendors like Teradata, Vertica, and SAP HANA offer both on-premises and cloud solutions. As more customers move to the cloud, cloud-native warehouses like Google Cloud BigQuery, Amazon Redshift, and Snowflake have gained popularity. These cloud warehouses leverage scalable infrastructure, such as object storage and serverless platforms, and integrate well with cloud services for easier data ingestion and processing.

Open-source data warehouses like Apache Hive, Trino, and Apache Spark have also adapted to the cloud. As data storage shifts to data lakes, these systems have separated into distinct components:

- **Query Engine**: Engines like Trino or Presto parse and execute SQL queries, often using distributed task execution frameworks like Apache Spark.
- **Storage Format**: Formats like Parquet or ORC define how data is encoded in files stored in object storage.
- **Table Format**: Formats like Apache Iceberg and Delta allow row inserts and deletions and provide features like time travel and transactions.
- **Data Catalog**: Services like Snowflake's Polaris define and manage tables within a database, supporting data discovery and governance.

### Column-Oriented Storage

Data warehouses typically use a relational schema with a large fact table and smaller dimension tables. Although fact tables may have over 100 columns, analytic queries usually access only a few of them. For example, consider this query that sums sales quantities for fruit and candy in 2024:

```sql
SELECT
  dim_date.weekday,
  dim_product.category,
  SUM(fact_sales.quantity) AS quantity_sold
FROM fact_sales
  JOIN dim_date    ON fact_sales.date_key   = dim_date.date_key
  JOIN dim_product ON fact_sales.product_sk = dim_product.product_sk
WHERE
  dim_date.year = 2024
  AND dim_product.category IN ('Fresh fruit', 'Candy')
GROUP BY
  dim_date.weekday, dim_product.category;

```

Traditional row-oriented storage stores entire rows together, so even when only a few columns are needed, the whole row is read. In contrast, column-oriented storage keeps data for each column separately. This means only the required columns are read, which greatly improves performance for analytic queries. Data is typically stored in blocks (often defined by date ranges), so the database only reads blocks overlapping the query’s criteria. This approach underpins formats like Parquet, ORC, and many analytic databases such as Snowflake and DuckDB.

### Column Compression

Column-oriented storage allows efficient compression, reducing disk and network demands. Since column values are often repetitive, compression techniques like **bitmap encoding** work well.

In bitmap encoding, a column with _n_ distinct values is represented by _n_ bitmaps—one for each value—where a bit is set to **1** if a row contains that value, otherwise **0**. These bitmaps can be further compressed using **run-length encoding** to store consecutive 0s and 1s efficiently. **Roaring bitmaps** dynamically switch between different encoding methods for optimal compression.

Bitmap indexes speed up queries, such as:

- `WHERE product_sk IN (31, 68, 69)`: Load and **bitwise OR** the corresponding bitmaps.
- `WHERE product_sk = 30 AND store_sk = 3`: Load and **bitwise AND** the bitmaps, as rows maintain the same order across columns.

This technique also applies to graph queries, such as finding mutual followers in a social network. However, **wide-column stores** (e.g., Bigtable, HBase) differ from column-oriented databases, as they store entire rows together despite their name.
![[Pasted image 20250330033224.png]]
**Sort Order in Column Storage**

In a column store, rows can be stored in insertion order for simplicity, but sorting them can improve indexing and query efficiency. Sorting must be done across entire rows, not independently per column, to maintain row alignment.

**Sorting Benefits:**

- Queries targeting date ranges (e.g., last month) benefit from sorting by `date_key`, allowing faster scans.
- A second sort key (e.g., `product_sk`) groups sales of the same product on the same day, optimizing filtering and grouping.
- Sorted data improves **compression**: long sequences of repeated values (especially in the primary sort key) enable efficient **run-length encoding**.

While later sort keys become more randomized, sorting the first few columns significantly boosts performance.

**Writing to Column-Oriented Storage**

Data warehouses typically see reads consisting of aggregations over many rows, which column-oriented storage, compression, and sorting help accelerate. Writes tend to be bulk imports via ETL.

Columnar storage makes individual row writes inefficient, but batched writes amortize the cost. A log-structured approach is often used, where writes first go to an in-memory store, then are periodically merged with column-encoded files on disk in bulk. Object storage is well-suited for storing these immutable data files.

Queries need to examine both the on-disk column data and recent in-memory writes, with the query engine handling this transparently. This approach is used by systems like Snowflake, Vertica, Apache Pinot, and Apache Druid.

## Query Execution: Compilation and Vectorization


Complex SQL analytics queries are broken into operators that can run in parallel across machines. Query execution can be optimized in two main ways:

1. Query Compilation:
- SQL query is converted to specific code
- Code is compiled to machine code
- Runs directly on column data in memory
- Similar to how JVM works
- Very efficient for specific queries

2. Vectorized Processing:
- Uses predefined operators to process batches of column values
- Instead of row-by-row processing, works on multiple values at once
- Example: Finding banana sales at a specific store:
  * Check product column for "bananas" → get bitmap
  * Check store column for store ID → get bitmap
  * Combine bitmaps with AND operation
  * Result shows all matching sales

Both approaches optimize for modern CPU features by:
- Favoring sequential memory access
- Using tight processing loops
- Leveraging parallel processing (threads and SIMD)
- Operating directly on compressed data
