# Organizing the folder strucure

## Default Next.js Folder Structure

```
next-js-app/
  ├── node_modules/   (dependencies)
  ├── package.json
  ├── pages/          (routing system)
  ├── public/         (static assets)
  └── styles/         (CSS, SASS, LESS)
```

## Customizing Your Structure

- You can move `pages/` and other directories into an `src/` folder
- This creates a cleaner root directory
- Exception: `public/` and `node_modules/` stay at root level

## Important Note

- If both `pages/` and `src/pages/` exist, Next.js prioritizes the root-level `pages/`
- This helps maintain backward compatibility

This organization approach makes your codebase more maintainable as it grows in complexity.

## Organizing the components

Follow the atomic design principle by creating these folders:

- **Atoms**: Basic components (buttons, inputs)
- **Molecules**: Small groups of atoms (input + label)
- **Organisms**: Complex structures (forms, footers)
- **Templates**: Page skeletons combining other components

For each component, create a dedicated folder with component file, test file, and style file.

## Organizing utilities

Group utility functions by purpose:

- Create files like `time.js`, `localStorage.js`, `jwt.js`, `logs.js`
- Add corresponding test files

## Organizing static assets

Structure your `public/assets/` folder with:

- `js/` for compiled JavaScript
- `css/` for compiled CSS
- `icons/` for favicons and web app icons
- `images/` for static images
- Create `manifest.json` in public folder for PWA support

We can easily create this manifest file by entering the **public/** folder and adding a new file called **manifest.json**:

`cd public/ && touch manifest.json`

At this point, we can fill the JSON file with some basic information. Let's take the following JSON as an example:

```json
{

  "name": "My Next.js App",

  "short_name": "Next.js App",

  "description": "A test app made with next.js",

  "background_color": "#a600ff",

  "display": "standalone",

  "theme_color": "#a600ff",

  "icons": [

    {

      "src": **"/assets/icons/icon-192.png"**,

      "type": "image/png",

      "sizes": "192x192"

    },

    {

      "src": **"/assets/icons/icon-512.png"**,

      "type": "image/png",

      "sizes": "512x512"

    }

  ]

}
```

We can include that file using an HTML meta tag, as seen in [_Chapter 3_](https://learning.oreilly.com/library/view/real-world-next-js/9781801073493/B16985_03_Final_SB_epub.xhtml#_idTextAnchor038), _Next.js Basics and Built-In Components_:

`<link rel="manifest" href=**"/manifest.json"**>`

That way, users browsing your Next.js app from a mobile device will be able to install it on their smartphones or tablets.

## Lib Files in Next.js

Lib files are specialized scripts that wrap third-party libraries, unlike utility scripts which are generic. Key differences:

- **Utility scripts**: Generic, reusable across many components
- **Lib files**: Specific to particular libraries or external services

## Example: GraphQL Integration

```
lib/
  └── graphql/
      ├── index.js          (client initialization)
      ├── queries/          (GraphQL queries)
      │   ├── query1.js
      │   └── query2.js
      └── mutations/        (GraphQL mutations)
          ├── mutation1.js
          └── mutation2.js
```

## Other Examples

Lib files can also be created for:

- Redis connections
- RabbitMQ integrations
- Other external library wrappers

## Benefits

This organization helps manage application state and supports dynamic components that render differently based on:

- Global application state
- Data from external services/APIs

A well-organized folder structure simplifies data flow management and makes your application more maintainable as it grows.

# Data fetching

- Use `getStaticProps` or `getServerSideProps` for server-side fetching
- Use HTTP clients like Axios for API integration
- Store sensitive data in `.env` files
- Handle API errors properly with status code checks

This organized structure helps maintain scalability and makes your codebase easier to navigate as it grows.

## Fetching data on the server side

1. Next.js allows you to fetch data on the server side using the built-in `getStaticProps` and `getServerSideProps` functions.

2. Since Node.js doesn't have built-in support for the JavaScript `fetch` API like browsers do, you have two options for making HTTP requests on the server:

   a. Using the Node.js built-in `http` library: This is a simple option, but requires a bit more work compared to using third-party HTTP client libraries.

   b. Using HTTP client libraries: These provide a more straightforward way to make HTTP requests from the server. Popular options include `isomorphic-unfetch` (which brings the `fetch` API to Node.js), `Undici` (an official Node.js HTTP 1.1 client), and `Axios` (a widely-used HTTP client that works on both the client and server).

3. The guide will focus on using `Axios` as the HTTP client, as it is one of the most popular options with around 17 million downloads per week on npm, and is likely to be a common choice for both client and server-side HTTP requests.

## Consuming REST APIs on the Server Side:

1. Next.js allows you to fetch data on the server side using the built-in `getServerSideProps` function.

2. You can use HTTP client libraries like Axios to make HTTP requests from the server. Axios is a popular choice as it works on both the client and server.

Example code:

```jsx
import { useEffect } from 'react';
import Link from 'next/link';
import axios from 'axios';

export async function getServerSideProps() {
  const usersReq = await axios.get('https://api.rwnjs.com/04/users');
  return {
    props: {
      users: usersReq.data
    }
  }
}

function HomePage({ users }) {
  return (
    <ul>
      {users.map((user) => (
        <li key={user.id}>
          <Link href={`/users/${user.username}`} passHref>
            <a>{user.username}</a>
          </Link>
        </li>
      ))}
    </ul>
  )
}

export default HomePage;
```

1. For private APIs that require authorization, you can pass the authorization token as a header in the Axios request:

```javascript
export async function getServerSideProps(ctx) {
  const { username } = ctx.query;
  const userReq = await axios.get(
    `${process.env.API_ENDPOINT}/04/users/${username}`,
    {
      headers: {
        authorization: process.env.API_TOKEN
      }
    }
  );

  if (userReq.status === 404) {
    return {
      notFound: true
    };
  }

  return {
    props: {
      user: userReq.data
    }
  };
}
```

1. It's recommended to store sensitive information like API tokens in environment variables (`.env` file) instead of hardcoding them in the codebase.

2. Next.js will automatically handle 404 errors by returning the default 404 page if the API returns a 404 status code.

The key takeaway is that Next.js makes it easy to fetch data on the server side using built-in functions like `getServerSideProps`, and you can use popular HTTP client libraries like Axios to make the requests, handling authorization and error cases as needed.

## Fetching data on the client side

Client-side Data Fetching:

1. Client-side data fetching is a crucial part of any dynamic web application, but it comes with additional complexities and vulnerabilities compared to server-side data fetching.

2. When making HTTP requests on the browser, you need to be extra cautious:
   - Make requests only to trusted sources after researching their security standards.
   - Use HTTPS for all API calls to avoid man-in-the-middle attacks.
   - Never connect directly to a remote database from the browser, as it exposes your users to high risk.

3. Fetching data on the server side hides sensitive information like API endpoints, parameters, headers, and authorization tokens from the users. However, doing it on the client side can reveal this private information, making it easier for attackers to perform various exploits.

4. The main advantage of client-side data fetching is that it can provide a more responsive and interactive user experience, as the data can be fetched and updated without a full page refresh.

5. However, the security risks involved in client-side data fetching mean that you need to be very careful in how you implement it. Proper measures, such as using trusted APIs, HTTPS, and avoiding direct database connections, are crucial.

The key takeaway is that while client-side data fetching can improve the user experience, it requires extra security considerations compared to server-side data fetching. Proper precautions must be taken to protect your application and users from potential attacks.

## Consuming REST APIs on the Client Side:

- Client-side data fetching is similar to server-side, using the browser's built-in `fetch` API or libraries like Axios:

```javascript
function Users() {
  const [loading, setLoading] = useState(true);
  const [data, setData] = useState(null);

  useEffect(async () => {
    const req = await fetch('https://api.rwnjs.com/04/users');
    const users = await req.json();
    setLoading(false);
    setData(users);
  }, []);

  return (
    <div>
      {loading && <div>Loading users...</div>}
      {data && <List users={data} />}
    </div>
  )
}
```

- Next.js doesn't force you to execute client-side requests differently than React.
- Client-side requests can run when the component mounts or after a particular event occurs.

**Challenges with Client-side Data Fetching:**

- CORS (Cross-Origin Resource Sharing) can block client-side requests to certain API endpoints.
- Exposing the authorization token in the client-side request headers can lead to security vulnerabilities.

**Solving the Challenges:**

- Create a Next.js API route to act as a proxy for the API request, handling the authorization and CORS issues on the server side:

```javascript
// pages/api/singleUser.js
import axios from 'axios';

export default async function handler(req, res) {
  const username = req.query.username;
  const userReq = await axios.get(
    `${process.env.API_ENDPOINT}/04/users/${username}`,
    { headers: { authorization: process.env.API_TOKEN } }
  );
  res.status(200).json(userReq.data);
}
```

- Then, refactor the client-side component to use the new API route:

```javascript
function UserPage({ username }) {
  const [loading, setLoading] = useState(true);
  const [data, setData] = useState(null);

  useEffect(async () => {
    const req = await fetch(`/api/singleUser?username=${username}`);
    const data = await req.json();
    setLoading(false);
    setData(data);
  }, []);

  return (
    <div>
      {loading && <div>Loading user data...</div>}
      {data && <UserData user={data} />}
    </div>
  );
}
```

The key takeaway is that client-side data fetching in Next.js requires careful consideration of security and CORS challenges, which can be addressed by using Next.js API routes as a proxy for the API requests.

## Consuming GraphQL APIs:

- GraphQL is a powerful alternative to REST APIs, providing benefits like avoiding over-fetching, single requests for multiple resources, and strong typing.
- We'll be using the Apollo Client library to integrate GraphQL in our Next.js application.

**Setting up Apollo Client:**

1. Install the required dependencies: `@apollo/client`, `graphql`, and `isomorphic-unfetch`.
2. Create an Apollo client instance in `lib/apollo/index.js` that can be used on both the client and server.
3. Wrap the entire Next.js app with the `ApolloProvider` in `pages/_app.js` to make the client available throughout the application.

**Fetching Data with GraphQL:**

1. Create GraphQL queries in `lib/apollo/queries/` directory, e.g., `getLatestSigns.js`.
2. Use the `useQuery` hook in your pages to execute the GraphQL queries and handle the loading, error, and data states.

Example:

```javascript
import { useQuery } from "@apollo/client";
import GET_LATEST_SIGNS from '../lib/apollo/queries/getLatestSigns'

function HomePage() {
  const { loading, error, data } = useQuery(GET_LATEST_SIGNS, {
    fetchPolicy: 'no-cache',
  });

  if (loading) {
    return <Loading />;
  }

  return (
    <div>
      {data.sign.map((sign) => (
        <Sign key={sign.uuid} {...sign} />
      ))}
    </div>
  );
}
```

**Mutations and Form Handling:**

1. Create GraphQL mutations in `lib/apollo/queries/addSign.js`.
2. Use the `useMutation` hook to execute the mutation when the user submits a form.
3. Handle the form state using the `useState` hook and pass the form data as the mutation variables.

Example:

```javascript
import { useState } from "react";
import { useMutation } from "@apollo/client";
import ADD_SIGN from "../lib/apollo/queries/addSign";

function NewSign() {
  const [formState, setFormState] = useState({});
  const [addSign] = useMutation(ADD_SIGN, {
    onCompleted() {
      router.push("/");
    }
  });

  const handleInput = ({ e, name }) => {
    setFormState({
      ...formState,
      [name]: e.target.value
    });
  };

  return (
    <div>
      <input
        id="nickname"
        type="text"
        onChange={(e) => handleInput({ e, name: 'nickname' })}
      />
      <button onClick={() => addSign({ variables: formState })}>
        Submit
      </button>
    </div>
  );
}
```

The key takeaways are:

1. Using Apollo Client makes it easy to integrate GraphQL in a Next.js application, handling both queries and mutations.
2. Organizing GraphQL-related code in a dedicated `lib/apollo/` directory keeps the codebase clean and maintainable.
3. Leveraging Next.js' server-side rendering capabilities, the Apollo client can be shared between the client and server for optimal performance.
