When discussing rendering strategies, we're referring to the methods used to deliver a web page (or application) to a web browser. Some frameworks, like Gatsby (as mentioned earlier), excel at serving statically generated pages, while others focus on server-side rendering.

Next.js takes these concepts further, offering the flexibility to choose whether a page should be rendered at build time or served dynamically at runtime. This allows for pages to be regenerated with each request, making certain parts of your application highly dynamic. Additionally, Next.js enables you to specify which components should be rendered only on the client side, enhancing the development experience.

In this chapter, we'll explore the following:

- How to implement server-side rendering for dynamic page rendering on each request
- Different approaches for rendering components exclusively on the client side
- Generating static pages during the build process
- Regenerating static pages in production using incremental static regeneration

# Server-side rendering (SSR)

![[Pasted image 20250224035629.png]]

Server-side rendering (SSR) is a traditional method of rendering web pages where the server generates the HTML before sending it to the browser. Next.js applies SSR by rendering pages dynamically on the server for each request and then sending the HTML to the browser. Afterward, JavaScript is used to hydrate the page, making it interactive.

SSR offers several benefits:

- **Security**: Sensitive data, like cookies or API calls, can be managed server-side, keeping it hidden from the client.
- **Compatibility**: The site works even if JavaScript is disabled or on older browsers.
- **SEO**: Search engines get HTML content immediately, improving SEO.

However, SSR has drawbacks:

- **Server load**: Every request requires re-rendering, leading to higher server costs.
- **Latency**: Fetching external data for each request can slow down page load times.
- **Navigation**: SSR can be slower than client-side rendering (CSR) or static pages, especially when switching between pages.

To implement SSR in Next.js, you can use the `getServerSideProps` function to fetch data on the server side for each request. This function fetches user data, passes it as props, and allows the page to be rendered with dynamic content. However, components relying on browser-specific APIs (e.g., `window` or `document`) must be rendered on the client side due to SSR limitations.

### Example: Dynamic User Greeting with SSR

```js
// pages/index.js

// getServerSideProps function to fetch user data from an API on the server
export async function getServerSideProps() {
  const userRequest = await fetch('https://example.com/api/user');
  const userData = await userRequest.json();

  return {
    props: {
      user: userData,  // Passing the fetched user data as props to the page component
    },
  };
}

// Page component that receives user data as props
function IndexPage(props) {
  return <div>Welcome, {props.user.name}!</div>;
}

export default IndexPage;
```

### Explanation:

1. **getServerSideProps**:
    - This asynchronous function is executed on the server for each request.
    - It fetches user data from an external API (`https://example.com/api/user`).
    - The data is then returned as `props` to the page component, making it available both on the client and server side.
2. **Page Component**:
    - The `IndexPage` function component receives the `user` prop, which contains the user data fetched by `getServerSideProps`.
    - It displays a greeting message, like `Welcome, John Doe!`, using the user data.
3. **Dynamic Rendering**:
    - Every time the page is requested, the server will fetch fresh user data and render the page with updated content.

This allows your page to be dynamically rendered for each request while benefiting from server-side rendering (SSR) and hydration, enabling the page to become interactive with client-side JavaScript once it is loaded.

# Client side rendering (CSR)

![[Pasted image 20250224040843.png]]

In a typical React app, as seen with tools like create-react-app (CRA), the page is rendered after the JavaScript bundle is transferred from the server to the client. Initially, the page appears empty (white) because CRA only serves basic HTML with a `<div id="root"></div>` container. The compiled JavaScript and CSS are injected into this HTML, and the app becomes interactive once the browser loads these files.

The main benefits of **Client-Side Rendering (CSR)** include:

- A native app-like experience with instant page navigation.
- Smooth page transitions without page reloads.
- Improved performance through lazy loading of components.
- Reduced server-side workload, allowing hosting on simpler or serverless environments.

However, CSR has some drawbacks:

- A slower initial load, especially for users with poor internet connections, since they must download the entire JavaScript bundle before seeing any content.
- SEO challenges, as search engine crawlers may find empty pages until JavaScript is executed, impacting performance scores.

Next.js addresses these issues by offering **Server-Side Rendering (SSR)** or **Static Site Generation (SSG)**, ensuring pages load faster and are more SEO-friendly. But, if you need browser-specific APIs like `window` or `document`, Next.js provides solutions to dynamically render those components only on the client-side.

## Using the React.useEffect hook

In modern React versions, especially with Next.js, the `useEffect` hook is commonly used in place of the older `componentDidMount` method. It allows you to perform side effects (such as data fetching or manipulating the DOM) inside function components, but only after the component has mounted. In Next.js, this means the `useEffect` callback will execute on the client side after React hydration, enabling client-only operations.

For example, consider a scenario where we want to use the Highlight.js library to display and highlight a code snippet. The code would typically look like this:

```jsx
import Head from 'next/head';
import hljs from 'highlight.js';
import javascript from 'highlight.js/lib/languages/javascript';

function Highlight({ code }) {
   hljs.registerLanguage('javascript', javascript);
   hljs.initHighlighting();

  return (
    <>
      <Head>
        <link rel='stylesheet' href='/highlight.css' />
      </Head>
      <pre>
        <code className='js'>{code}</code>
      </pre>
    </>
  );
}

export default Highlight;
```

However, this would fail in Next.js during the build phase because `Highlight.js` requires the `document` global variable, which is only available in the browser. To solve this, you can move the `Highlight.js` initialization into the `useEffect` hook, like so:

```jsx
import { useEffect } from 'react';
import Head from 'next/head';
import hljs from 'highlight.js';
import javascript from 'highlight.js/lib/languages/javascript';

function Highlight({ code }) {
  useEffect(() => {
    hljs.registerLanguage('javascript', javascript);
    hljs.initHighlighting();
  }, []);

  return (
    <>
      <Head>
        <link rel='stylesheet' href='/highlight.css' />
      </Head>
      <pre>
        <code className='js'>{code}</code>
      </pre>
    </>
  );
}

export default Highlight;
```

Now, `Highlight.js` will run only on the client side after the component is mounted, preventing errors during server-side rendering.

You can also render components exclusively on the client side by using both `useEffect` and `useState`. Here's an example of how to do this:

```jsx
import { useEffect, useState } from 'react';
import Highlight from '../components/Highlight';

function UseEffectPage() {
  const [isClient, setIsClient] = useState(false);

  useEffect(() => {
    setIsClient(true);
  }, []);

  return (
    <div>
      {isClient && (
        <Highlight
          code={"console.log('Hello, world!')"}
          language='js'
        />
      )}
    </div>
  );
}

export default UseEffectPage;
```

In this example, the `Highlight` component will only render on the client side, ensuring that the library interacts with the DOM as expected.

## Using dynamic component loading

Next.js offers a built-in `dynamic` function, which provides an interesting alternative to rendering components client-side. For example, using the `dynamic` function, we can load the `Highlight` component only on the client side:

```jsx
import dynamic from 'next/dynamic';

const Highlight = dynamic(
  () => import('../components/Highlight'),
  { ssr: false }
);

import styles from '../styles/Home.module.css';

function DynamicPage() {
  return (
    <div className={styles.main}>
      <Highlight
        code={"console.log('Hello, world!')"}
        language='js'
      />
    </div>
  );
}

export default DynamicPage;
```

In this code, we use `dynamic` to import the `Highlight` component, specifying `{ ssr: false }` to prevent server-side rendering. As a result, Next.js will only render this component once React hydration occurs on the client side.

Client-side rendering (CSR) can be a great alternative to server-side rendering (SSR) for building dynamic web pages, particularly for pages that don't need to be indexed by search engines (like admin or private profile pages). With CSR, we can load the JavaScript first and then fetch data on the client side, reducing the server workload and enabling better scalability.

The next section will explore the possibility of sending a static page to the client and fetching the data after it's loaded in the browser.

# Static site generation

Next.js provides a third option for rendering web apps: **Static Site Generation (SSG)**. SSG allows specific pages (or entire websites) to be pre-rendered at **build time**. Pages that don’t change frequently can be served as static assets, with the React hydration process making them interactive once served.

### Advantages of SSG:

- **Easy scalability:** Static pages are just HTML files, which can be easily served by a Content Delivery Network (CDN), reducing server load.
- **Outstanding performance:** As HTML is pre-rendered, there's no runtime rendering on each request, reducing latency.
- **More secure:** No need to send sensitive data to the server for rendering, as all data is part of the pre-rendered HTML.

However, the downside of traditional SSG is that once a page is built, its content remains unchanged until the next deployment. Next.js solves this problem using **Incremental Static Regeneration (ISR)**. ISR allows a page to be re-rendered after a specified period, updating its content without rebuilding the entire site.

### Example of ISR in Next.js:

```javascript
import fetch from 'isomorphic-unfetch';
import Dashboard from './components/Dashboard';

export async function getStaticProps() {
  const userReq = await fetch('/api/user');
  const userData = await userReq.json();

  const dashboardReq = await fetch('/api/dashboard');
  const dashboardData = await dashboardReq.json();

  return {
    props: {
      user: userData,
      data: dashboardData,
    },
    revalidate: 600, // revalidate after 10 minutes
  };
}

function IndexPage(props) {
  return (
    <div>
      <Dashboard user={props.user} data={props.data} />
    </div>
  );
}

export default IndexPage;
```

In this example:

- `getStaticProps` is called at **build time** to fetch data and generate the page.
- The `revalidate` option specifies how often the page should be re-rendered after the build (in this case, every 600 seconds or 10 minutes).
- During the 10 minutes, all users will see the same static page. After 10 minutes, if a new request occurs, the page is re-rendered and cached again.

SSG combined with ISR allows for **hybrid rendering**, where some pages are statically generated, and others can still be dynamically fetched at request time (SSR). This combination is powerful for creating fast, scalable, and dynamic websites.
