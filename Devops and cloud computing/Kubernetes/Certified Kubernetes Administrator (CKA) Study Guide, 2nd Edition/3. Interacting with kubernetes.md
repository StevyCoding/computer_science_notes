# API Primitive and Objects
- primitive
	- they are the basic building blocks of kubernetes sys
	- Define what kubernetes manage and  how
	- Example : Pod, Service, Namespace, Node
- Objects
- These are record of intent; you describe what you want ( in YAML/JSON), and Kubernetes makes it happen
- Object are instance of primitive

## 🔹 API Version

Defines the version of the Kubernetes API used for the object (like a schema). It follows a maturity model: `alpha` → `beta` → `stable`. Example: `apps/v1`.

---

## 🔹 Kind

Specifies the type of Kubernetes object (e.g., `Pod`, `Service`, `Deployment`).

---

## 🔹 Metadata

Contains identifying info like `name`, `namespace`, `labels`, and `annotations`.

---
## 🔹 Spec

Describes the desired state of the object (e.g., container image, replicas, ports).

---
## 🔹 Status

Reflects the current state of the object, updated by the Kubernetes system to show if it matches the desired spec.
# Using Kubectl

- primary tool to interact with kubernetes cluster from cmd
- kuberctl execution consist of a command; a resource type  a resource name; and optional command line flags

```bash
kubectl [command] [TYPE] [NAME] [flag]
```

- **Command**: Action to perform (e.g., `create`, `get`, `describe`, `delete`).
    
- **Resource Type**: The kind of object (e.g., `service` or short form `svc`).
    
- **Name**: The object's `metadata.name`, unique within its namespace (not the same as UID).
    
- **Flags**: Optional settings (e.g., `--port`) to customize behavior.

# Manage Object

- You can create object in kubernetes cluster in two ways:
- imperatively and declaratively
## Imperative object management
- don't require a manifest definition
- using kubectl to manage the objects with a single command
### Creating object
creating a pod named frontend who listen to port 80
```bash
kubectl run frontend --image=nginx:1.24.0 --port=80
```
### Updating object
- can still modify the objects cfg with `patch` and `edit` commands
- **edit**
	- opens  edit commmand opens an editor  (vi or nano) with the raw configuration of the live obect
```bash
$ kubectl edit pod frontend
```
- **patch**
	- apply change progammatically (JSON or stategic merge)
	- the -p flag define the json structure used to modify the live object
```bash
$ kubectl patch pod frontend -p '{"spec":{"containers":[{"name":"frontend",\
"image":"nginx:1.25.1"}]}}'
```

### Deleting objects
The following command delete obeject  :
```bash
$ kubectl delete pod frontend
```
- with this cmd kubernetes delete the object gracefully; so that there is a minimal impact to the user (if the object is not deleted during 30 sec kubernetes forcefully kill the object)
- During the exam you can delete fast the object using `--now` option; example :
```bash
$ kubectl delete prod nginx --now
```

## Declarative object Management
- the declarative object management require one or several manifests (YAML or JSON) describing the desired state of an object.
- You can create; update; delete object using this approach
- it's a recommended way to create objects in production environment

### Creating  objects
- creating object from a manifest from YAML  using `apply`
- `-f` option specify a directory of file, a file or a  file refenced by a HTTP URL;
```.
├── app-stack
│   ├── mysql-pod.yaml
│   ├── mysql-service.yaml
│   ├── web-app-pod.yaml
│   └── web-app-service.yaml
├── nginx-deployment.yaml
└── web-app
    ├── config
    │   ├── db-configmap.yaml
    │   └── db-secret.yaml
    └── web-app-pod.yaml
```
- creating an object from a single file
```bash
$ kubectl apply -f nginx-deployment.yaml
```
- creating an object from multiple files within a directory
```bash
$ kubectl apply -f app-stack/
```
- creating an object from a recursuve directory tree containing files
```bash
$ kubectl apply -f web-app/ -R
```
- Creating objects from a file referenced by an HTTP(S) URL:
```bash
$ kubectl apply -f https://raw.githubusercontent.com/bmuschko/\
cka-study-guide/master/ch03/object-management/nginx-deployment.yaml
```
The `apply` command keeps track of the changes by adding or modifying the annotation with the key `kubectl.kubernetes.io/last-applied-configuration`. Here’s an example of the annotation in the output of the `get pod` command:
```bash
$ kubectl get pod web-app -o yaml
apiVersion: v1
kind: Pod
metadata:
  annotations:
    kubectl.kubernetes.io/last-applied-configuration: |
      {"apiVersion":"v1","kind":"Pod","metadata":{"annotations":{}, \
      "labels":{"app":"web-app"},"name":"web-app","namespace":"default"}, \
      "spec":{"containers":[{"envFrom":[{"configMapRef":{"name":"db-config"}}, \
      {"secretRef":{"name":"db-creds"}}],"image":"bmuschko/web-app:1.0.1", \
      "name":"web-app","ports":[{"containerPort":3000,"protocol":"TCP"}]}], \
      "restartPolicy":"Always"}}
...
```

### Updating 
Just Change the configuration file and run the apply command again

### Deleting Objects

While you can delete objects using the `apply` command by providing the options `--prune -l <labels>`, it is recommended to delete an object using the `delete` command and point it to the configuration file. The following command deletes a Deployment and the objects it controls (ReplicaSet and Pods):
```bash
$ kubectl delete -f nginx-deployment.yaml
deployment.apps "nginx-deployment" deleted
```
### Hybrid Approach

You can generate a YAML manifest without creating the object by using a **hybrid approach**:  
Use `--dry-run=client` with `-o yaml` to preview the config.

Example:

```bash
kubectl run nginx --image=nginx --dry-run=client -o yaml > pod.yaml
```

This creates a YAML file you can edit and apply later.

## Which Approach to Use?

During the exam, using imperative commands is the most efficient and quick way to manage objects. Not all configuration options are exposed through command-line flags, which may force you into using the declarative approach. The hybrid approach can help here.

# Summary

Kubernetes represents its functionality for deploying and operating a cloud-native application with the help of primitives. Each primitive follows a general structure: the API version, the kind, the metadata, and the desired state of the resources, also called the spec. Upon creation or modification of the object, the Kubernetes scheduler automatically tries to ensure that the actual state of the object follows the defined specification. Every live object can be inspected, edited, and deleted.

`Kubectl` acts as a CLI-based client to interact with the Kubernetes cluster. You can use its commands and flags to manage Kubernetes objects. The imperative approach provides a fast turnaround time for managing objects with a single command, as long as you memorize the available flags. More complex configuration calls for the use of a YAML manifest to define a primitive. Use the declarative command to instantiate objects from that definition. The YAML manifest is usually checked into version control and offers a way to track changes to the configuration.
