# Understanding extension Interfaces

- Kubernetes architecture has been design to be :
	- flexible
	- modular
	- extensible
- You can extend the cluster using extensions
- extension are component that can be plugged into the platform to support custom functionality not native to Kubernetes (network plugin, device plugin, storage plugin)
In this section, we are going to talk about **critical interfaces**, you will need to understand as a Kubernetes administator:
- Container Network Interface (CNI)
- Container Runtime Interface (CRI)
- Container Storage Interface (CSI)

## Container Network Interface (CNI)
CNI is a spec and library for configuring container networking in Linux.  
In Kubernetes, it enables Pod-to-Pod communication.  
A CNI plugin must be installed on control plane nodes for networking to work.
## Container Runtime Interface (CRI)
The container runtime manages container lifecycles and resources. 
Kubernetes uses **containerd** by default but supports others via the **CRI**, which connects Kubernetes to different runtimes.
## Container Storage Interface (CSI)
Although Kubernetes provides a Volume plugin system, it was hard to integrate third-party storage solutions. In response, CSI was developed to as a standard to implement plugins for integrating arbitrary block and file storage systems to containerized workloads.
